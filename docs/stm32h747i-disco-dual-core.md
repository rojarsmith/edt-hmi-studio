# STM32H747I-DISCO: dual-core handling

The STM32H747XI carries two cores — a Cortex-M7 at up to 480 MHz and a
Cortex-M4 at up to 240 MHz — but the HMI generated by this editor is a
**single application that runs entirely on the Cortex-M7**. The Cortex-M4 has no
firmware of its own.

That combination has one prerequisite you have to set once per board, and this
document explains what it is, why it is needed, and how to check it.

## What the firmware template assumes

| Item | Value |
| --- | --- |
| Application core | Cortex-M7 |
| Image load address | `0x08000000` (Flash bank 1) |
| Cortex-M4 | Boot disabled at the option bytes (`BCM4 = 0`) |
| CMSIS system file | `system_stm32h7xx_dualcore_bootcm7_cm4gated.c` |
| SYSCLK | 400 MHz from the 25 MHz HSE crystal |
| Frame buffers | SDRAM at `0xD0000000`, two of them |
| Modbus UART | USART1 on PA9/PA10, wired to the ST-LINK VCP |

`system_stm32h7xx_dualcore_bootcm7_cm4gated.c` is ST's own template for exactly
this arrangement: *"Cortex-M7 boot is enabled at FLASH option bytes, Cortex-M4
boot is disabled at FLASH option bytes, Cortex-M4 boot can be enabled by the
Cortex-M7 (when needed)"*. Choosing it is what makes the M7-only image the
standard configuration rather than an improvisation.

## The one-time option-byte change

Boards ship from the factory with **both** cores enabled (`BCM7 = 1`,
`BCM4 = 1`). With that setting the Cortex-M4 starts from Flash bank 2 at
`0x08100000`. This firmware never writes bank 2, so the M4 fetches whatever is
there — on an erased device, `0xFFFFFFFF` — and faults immediately.

A faulted M4 does not corrupt the M7's application, and in practice the HMI
still runs. But the M4 is then sitting in an undefined state, which makes the
board hard to reason about when something else goes wrong, and it keeps domain
D2 clocked for reasons that have nothing to do with your application. Disable
its boot instead:

```bash
STM32_Programmer_CLI -c port=SWD mode=UR -ob BCM4=0
```

Read the setting back to confirm:

```bash
STM32_Programmer_CLI -c port=SWD mode=UR -ob displ
```

`BCM7` must stay `1` and `BCM4` must read `0`. The change survives power cycles
and only has to be done once per board.

### Undoing it

If you later want to run a Cortex-M4 application again:

```bash
STM32_Programmer_CLI -c port=SWD mode=UR -ob BCM4=1
```

## Why the firmware still tolerates the factory setting

`board_init()` waits, with a bounded timeout, for domain D2 to report ready
before it touches the clock tree:

```c
while ((__HAL_RCC_GET_FLAG(RCC_FLAG_D2CKRDY) == RESET) && (timeout-- > 0U)) {
}
```

With `BCM4 = 0` the flag settles almost immediately. With the factory setting it
settles once the M4 has booted and faulted. Either way the M7 gets a defined
starting point instead of racing the second core, so a board whose option bytes
have not been changed yet will still come up — it is just not the configuration
this template is designed around.

USART1 lives in domain D2, so if D2 never became ready Modbus would be the first
thing to stop working. That is why the timeout path force-enables the domain
rather than hanging.

## Flash budget

The editor's board definition reports **1 MB** of Flash for this board, not the
2 MB printed on the datasheet. That is deliberate: 2 MB is the total across both
banks, and only bank 1 belongs to this image. Generated images and fonts are
linked into bank 1, so 1 MB is the number that matters when the editor warns you
that a project will not fit.

A build of the reference project uses roughly:

```
   text    data     bss
 759608     760  279484
```

— about 74% of bank 1, and 55% of the 512 KB AXI SRAM that holds `.bss`.

## Display and touch

The panel is the MB1166 daughterboard: an 800×480 TFT driven over **MIPI-DSI**
through an OTM8009A controller, which is a different arrangement from the
parallel-RGB LTDC on the STM32F746G-DISCO. Touch is an FT6X06 on I²C.

Both are brought up through ST's second-generation BSP, so the calls are
instance-based (`BSP_LCD_InitEx(0, ...)`, `BSP_TS_GetState(0, &state)`) rather
than the parameterless v1 API the F7 template uses. Two consequences worth
knowing:

- `BSP_LCD_Init()` defaults to **RGB888**. The template calls `BSP_LCD_InitEx()`
  with `LCD_PIXEL_FORMAT_RGB565` instead, halving both the SDRAM footprint and
  the bandwidth the LTDC needs per frame.
- `BSP_LCD_InitEx()` brings up the SDRAM controller itself, so there is no
  separate `BSP_SDRAM_Init()` call.

The display driver uses two full frame buffers in SDRAM and swaps them during
vertical blanking:

```c
BSP_LCD_Reload(0, BSP_LCD_RELOAD_NONE);          /* once, at init */
...
BSP_LCD_SetLayerAddress(0, 0, (uint32_t)buffer); /* staged, not applied */
BSP_LCD_Reload(0, BSP_LCD_RELOAD_VERTICAL_BLANKING);
```

With reloading switched off, `BSP_LCD_SetLayerAddress` routes to
`HAL_LTDC_SetAddress_NoReload`, so the address only takes effect at the next
vertical blanking. A frame is therefore never displayed while it is being drawn.

## MPU configuration

`board_init()` re-types the SDRAM window at `0xD0000000` as Normal write-back
memory before enabling the caches. Without it the Cortex-M7 default memory map
treats that range as **Device** memory: uncacheable, and writes may not be
merged. Streaming a frame buffer through Device memory costs far more FMC
bandwidth than it should, starves the LTDC, and shows up on the panel as tearing
and warped lines whenever anything redraws continuously.

The display driver cleans the D-Cache over the finished frame before handing the
buffer to the LTDC, which reads SDRAM directly.

## Every interrupt the BSP enables needs a handler

`stm32h7xx_it.c` must define a handler for each interrupt the BSP turns on. An
unhandled one vectors to the startup file's `Default_Handler`, which is an
infinite loop: the core stops there and never returns, so the display freezes
mid-frame and the main loop — Modbus included — never runs again.

This board needs at least:

```c
void LTDC_IRQHandler(void)    { HAL_LTDC_IRQHandler(&hlcd_ltdc); }
void LTDC_ER_IRQHandler(void) { HAL_LTDC_IRQHandler(&hlcd_ltdc); }
void DSI_IRQHandler(void)     { HAL_DSI_IRQHandler(&hlcd_dsi); }
```

`hlcd_ltdc` and `hlcd_dsi` are exported by `stm32h747i_discovery_lcd.h`.

`BSP_LCD_InitEx()` enables the LTDC register-reload interrupt, which fires on
every buffer swap. Without `LTDC_IRQHandler` the very first flush hangs the
firmware, and the symptom is an entirely **white screen** — the panel has been
initialised but nothing was ever drawn. Nothing about that appearance points at
interrupts, which is what makes it worth writing down.

## Diagnosing a hang from the symptom

Attaching a debugger reads the answer straight off the chip and beats guessing.
Start the GDB server against the running target without resetting it:

```bash
ST-LINK_gdbserver -p 61234 --swd --attach --persistent -cp <CubeProgrammer>/bin
```

Then read where the core actually is:

```bash
arm-none-eabi-gdb --batch <build>/firmware.elf \
  -ex "target extended-remote localhost:61234" \
  -ex "info registers pc lr sp" -ex "bt 12" -ex "detach"
```

Interpreting it:

- **PC in `HAL_Delay` with a sane backtrace** — the firmware is running normally;
  the problem is elsewhere (a peripheral setting, or the data being sent).
- **PC in `Default_Handler`** (GDB may name it after whichever IRQ symbol is
  aliased to it, e.g. `WWDG_RST_IRQHandler`) **with `lr = 0xffffffe9`** — an
  exception was taken and there is no handler for it. Identify which one:

  ```bash
  -ex "x/1xw 0xE000ED04"   # SCB->ICSR; VECTACTIVE is bits 8:0
  ```

  `IRQ number = VECTACTIVE - 16`. Look that up in `stm32h747xx.h` — for example
  `0x068` is 104, so IRQ 88, which is `LTDC_IRQn`. `NVIC->ISER` at `0xE000E100`
  shows which interrupts are enabled if you need to narrow it down further.
- **PC inside an LVGL function, spinning** — `LV_ASSERT_HANDLER` is `while (1);`,
  so any LVGL assertion (a failed allocation, most often) stops everything.

Reading peripheral registers the same way is usually quicker than adding trace
output. `LTDC->ISR`/`IER` at `0x50001034` tell you whether a reload completed or
the FIFO underran; a runtime configuration struct read back from RAM tells you
what the firmware actually applied rather than what the project intended.

### Touch orientation

`BSP_TS_Init` is called with `TS_SWAP_XY | TS_SWAP_Y` for this panel. The
FT6X06 reports the display's native **portrait** frame — X spanning 0..480,
Y spanning 0..800 — so both transforms are needed: `TS_SWAP_XY` puts the
800-wide axis on screen X, and `TS_SWAP_Y` corrects the remaining axis, which
otherwise runs bottom-to-top.

`Width`/`Height` stay 800x480 and are matched by `FT6X06_MAX_X_LENGTH` /
`FT6X06_MAX_Y_LENGTH` in `ft6x06_conf.h`. Those look transposed against the raw
ranges, and must be: the BSP scales with `Width / MaxX` *after* swapping, so
`MaxX` has to describe whichever axis ends up on X. "Correcting" them to match
the sensor breaks the scaling instead of fixing it.

**Do not deduce this from behaviour.** Symptoms overlap badly: a missing
`TS_SWAP_XY` and a missing `TS_SWAP_Y` both present as "the wrong part of the
screen responds", and fixing one alone can look like a regression. Measure it —
see below.

One symptom is worth recognising because it is unambiguous: a missing
`TS_SWAP_XY` makes `MaxY - rawY - 1` underflow for every `rawY > 479`, and the
unsigned result surfaces as coordinates around **8947848 - k**. Huge numbers in
that range mean the axes are crossed, not that the sensor is faulty.

### Measuring the mapping

`board_touch_log` in `board_display.c` records touches for exactly this. Flash,
touch the four corners in a known order, then read it:

```bash
x/5dw &board_touch_log    # presses, min_x, max_x, min_y, max_y
x/8dw &board_touch_log.recent
```

`min`/`max` show the reachable range — if `max_x` stops near 480 on an 800-wide
panel, the sensor's X is the short axis and the frames are crossed. `recent`
holds the last four presses at index `presses & 3`, so with 11 presses the
chronological order is `recent[3], recent[0], recent[1], recent[2]`.

Invert the transform currently in force to recover the raw values, then check
each axis separately: left-hand corners should give small X, top corners small
Y. An axis where the corners come out reversed needs its mirror flag.

The BSP also keeps state in RAM. Read `Ts_Ctx` (find its address with
`arm-none-eabi-nm`) and decode it as:

| Offset | Field |
| --- | --- |
| 0 | `Width` |
| 4 | `Height` |
| 8 | `Orientation` |
| 12 | `Accuracy` |
| 16 | `MaxX` |
| 20 | `MaxY` |
| 24 | `PreviousX[0]` |
| 28 | `PreviousY[0]` |

`PreviousX` and `PreviousY` are **arrays** of `TS_TOUCH_NBR` entries, which is 2
here — so `PreviousY[0]` is at offset 32, not 24. Reading offset 28 as a Y
coordinate gives you `PreviousX[1]`, an unused second-touch slot that
`BSP_TS_Init` fills with `Width + Accuracy + 1` (806) and `Height + Accuracy + 1`
(486). Those sentinels look exactly like out-of-range coordinates and will send
you after the wrong axis.

## Clock and supply settings that must not be improvised

Two lines in `system_clock_config()` look like details and are not. Both fail in
ways that point nowhere near the clock tree.

**The supply must be selected before voltage scaling can complete.** The part
leaves reset in "Run*" mode with neither regulator committed, and `VOSRDY` stays
clear until something writes `PWR->CR3`. Skip that and this loop never exits:

```c
__HAL_PWR_VOLTAGESCALING_CONFIG(PWR_REGULATOR_VOLTAGE_SCALE1);
while (!__HAL_PWR_GET_FLAG(PWR_FLAG_VOSRDY)) { }   /* hangs forever */
```

The symptom is a board that flashes cleanly and then shows **nothing at all** —
no backlight change, no partial frame — because `board_init()` never returns.

ST's examples do not call `HAL_PWREx_ConfigSupply()`, which makes it look
optional. It is not: they get the same register write from the CMSIS
`ExitRun0Mode()`, and every branch of that function is wrapped in
`#if defined(USE_PWR_...)`. Without one of those macros defined at build level
it compiles to an empty function. This template calls
`HAL_PWREx_ConfigSupply(PWR_LDO_SUPPLY)` explicitly instead, so the behaviour
does not depend on a preprocessor define being carried along with the project.

**Use `FLASH_LATENCY_4`.** The VOS1 wait-state table suggests 2 wait states for
a 200 MHz AXI clock, and ST's examples still use 4. With too few, instruction
fetches return corrupted data, and the failures look like anything but a clock
problem.

### A software reset is not a power-on reset

`PWR->CR3` can only be written once **per power-on reset**, and the programmer
ends a flash with a software reset:

```
MCU Reset
Software reset is performed
```

So the first run after plugging the board in behaves differently from every run
after a re-flash: on the later ones the supply is already committed, and
`HAL_PWREx_ConfigSupply()` reports an error for a configuration that is in fact
fine. Treating that as fatal makes the board work once and then apparently die
on the next flash — which reads like a regression in whatever changed most
recently, and is not.

Call it, ignore the result, and let the voltage-scaling wait decide whether the
supply is usable.

### Nothing on the start-up path may wait forever

Every wait in `board_init()` is bounded, and failures are reported rather than
parked in a spin loop. A board stuck early draws nothing and answers nothing,
and is *harder* to inspect than one that reached the main loop degraded — the
debugger has to contend with a running core either way, but a firmware that
reaches `HAL_Delay()` can at least be read for state. `board_error_handler()`
belongs in fault handlers, not in the response to a peripheral that came up
unexpectedly.

## Recovering a board that no longer accepts a connection

`Error: Unable to get core ID` / `No STM32 target found`, while the tool still
reports the ST-LINK's serial number, firmware version and 3.28 V, means the
probe is healthy and only the core is unreachable.

Work through these in order; stop as soon as a connection succeeds.

**1. Release the debug interface.** A GDB server left running holds the probe,
and killing one without detaching first can leave its state inconsistent. Kill
any `ST-LINK_gdbserver` process, then retry.

**2. Re-plug the ST-LINK USB.** Forcibly killing a debug session can leave the
probe's internal state inconsistent; re-enumerating it clears that.

**3. Fully power-cycle the board.** Unplug every USB lead, wait ten seconds,
reconnect. This is the only way out of Standby, which is where a misbehaving
image can strand the device.

**4. Connect under reset, so the firmware never gets to run:**

```bash
STM32_Programmer_CLI -c port=SWD mode=UR
```

**5. Hold the RESET button** while starting that command and release it once the
tool prints the supply voltage.

**6. Boot the system bootloader with BOOT0.** If user code still wins the race,
this stops it running at all. On the STM32H747I-DISCO **BOOT0 is exposed at
resistor R192, which sits underneath the LCD panel** — the panel is removable,
and the board's user manual has the layout. Bridging the R192 pads pulls BOOT0
high, so the part starts the built-in bootloader instead of your image, and the
programmer can always connect. Erase or re-flash, then remove the bridge.

Once connected, disable the Cortex-M4 boot before flashing anything else, so a
second core is not running whatever happens to be in the erased Flash bank 2:

```bash
STM32_Programmer_CLI -c port=SWD mode=UR -ob BCM4=0
```

## Things to check first if the board looks dead

1. **Option bytes.** `-ob displ` should show `BCM7=1`, `BCM4=0`.
2. **A white screen usually means a hang, not a display fault.** Check for a
   missing interrupt handler as described above.
3. **`Unable to get core ID` is not a probe fault.** If the ST-LINK still
   reports its serial number and 3.28 V, the probe is healthy and the core is
   unreachable — work through the recovery steps above, starting with a full
   power cycle.
3. **Modbus baud rate.** The generated `hmi_bindings_generated.c` carries what
   the project's Communication panel is set to. If the peer disagrees you get
   framing errors and all-zero bytes on the wire, not a silent link.
4. **LVGL asserts halt everything.** `lv_timer_handler()` shares the main loop
   with `hmi_runtime_task()`, so an LVGL assertion stops Modbus too. If the UART
   goes completely silent rather than merely wrong, suspect an assert.
5. **Check which build you flashed.** Build directories accumulate under
   `.hmi-builds/`; each carries a `build-metadata.json` with its board and
   timestamp, and a `project-source/project.json` with the pages and events it
   was generated from. A control that does nothing is often an older image.

# 影片播放——從 SD 卡上把一部片子讀出來

<p align="center">
  <a href="../video-playback.md">English</a> · <strong>繁體中文</strong>
</p>

這個編輯器裡的其他每一個元件，內容都是專案自己擁有的東西：標籤的文字、圖片的
像素、圖表的數字。它們全都會被編進韌體映像檔，燒進板子裡。

影片沒辦法這樣做。一分鐘的 800×480 影像大約 200 MB——是那塊要播它的板子內部
Flash 的兩百倍。所以 Video 是唯一一個**指名內容而不是帶著內容**的元件：你打上
一個檔名，面板在執行期自己到 SD 卡上把那個檔案找出來。

以下的一切，都是從這一個決定長出來的。

---

## 1. 這個元件是什麼

從 **Miscellaneous（雜項）** 分類把 **Video** 拖出來，它會落成一塊黑色矩形——
也就是畫面將要佔住的那個框。它只有三個屬性，沒有別的：

| 屬性 | 預設 | 作用 |
| --- | --- | --- |
| **Source** | Files I name | 一行一個檔案的清單，或 **Every .avi in a folder**——掃描卡片上的一個資料夾。 |
| **Files on the SD card** | *(空白)* | 播放清單，照播放順序排。每一項是檔案的名字，若在資料夾裡就把資料夾寫在前面——`intro.avi`、`clips/morning.avi`。正反斜線都收；Windows 使用者照自己螢幕上看到的打就行。 |
| **Folder on the SD card** | *(空白——卡片最上層)* | 資料夾掃描：裡面每一個 `.avi` 都會播，照名稱排序。 |
| **Auto Play** | 開 | 載入帶著這個元件的畫面時就開始播。 |
| **Loop** | 開 | 播完最後一個檔案之後，整份清單從頭再來。只有一個檔案時就是那部片循環。 |
| **Random order** | 關 | 下一個檔案用亂數挑——軟體亂數序列，每次開機種子都不同——而且**絕不會是剛播完的那一個**。Loop 關閉時，清單有幾個檔案就播幾部，然後停下。清單只有一個檔案時這個開關是灰的：一個檔案沒有順序可以打亂。 |

只有一個檔案的清單，行為和從前的單一檔案完全一樣；在播放清單出現之前存的專案帶著
舊的 `fileName`，照舊播放。

沒有匯入步驟，沒有資源條目，也不會有任何東西被加進建置。一部兩小時的片子花掉的
韌體空間，和兩秒鐘的一模一樣：零。要換影片就換卡片上的檔案，不必重新建置。

代價是編輯器從來沒看過那些檔案，也查不了它們。所以它只查不管卡片上有什麼都一樣錯
的事——一個檔案都沒填、某一項的副檔名不是 `.avi`、同一個檔案列了兩次——其餘全部
留給面板，因為只有面板真的能去看。資料夾掃描則完全不查：資料夾裡有什麼，是面板才
找得出來的事。

### 清單怎麼前進

一個檔案從頭播到尾，然後挑下一個。除非開了 Random order，否則由上往下照順序。打不
開的檔案——從卡片上刪掉了、格式不對——**跳過，不是致命錯誤**：播放清單是一組各自
獨立的影片，壞掉的那個成員被略過。只有在每一個檔案都失敗時，元件才顯示原因。資料夾
掃描最多收 64 個檔案；掃描發生在元件開始播放的時候，所以換上放了新檔案的卡片，下次
進到這個畫面就會撿到。

## 2. 哪些板子播得動

| 板子 | 影片 | 原因 |
| --- | --- | --- |
| **STM32H747I-DISCO** | ✅ | 有 JPEG 編解碼硬體，也有接在 SDMMC1 上的 4-bit microSD 插槽。 |
| STM32F746G-DISCO | ❌ | 沒有 JPEG 硬體。那個週邊是 F76x/F77x 才開始有的。 |
| EDT EVK043027B | ❌ | STM32U599 沒有 JPEG 硬體，板子上也沒有外部 RAM 可以放影格緩衝區。 |

這不是「驅動還沒寫」。一秒解二十四張 800×480 的 JPEG，**同時還要跑一整套使用者
介面**，不是 Cortex-M7 用軟體做得到的事——根本沒有一條比較慢的路可以退。沒有那顆
硬體的板子就是播不動影片，把這件事講清楚才是誠實的答案。

所以它的處理方式，和「尚未實作的通訊協定」與「驅動不了的螢幕方向」完全一樣：元件
在任何板子上都能放、能設定、能預覽、能存檔，而**用到它的專案在沒有 JPEG 硬體的板子
上不能建置**。屬性面板的 Video 區塊會說明是哪一種情況，Deploy 分頁也會用同樣的話
擋下建置——擋在編譯器之前，而不是變成一句找不到標頭檔的訊息。

**板子的能力只寫在一個地方**：[`src/types/hmi.ts`](../../src/types/hmi.ts) 裡的
`BoardDefinition.video`。要讓第四塊板子播影片，就是把那個欄位填上、給它一份執行期
程式；編輯器其他地方一行都不用動。

[§10](#10-這個硬體相依到底有多硬) 把這份相依一層一層拆開，說明哪些部分可以搬到別的
板子、哪些不行，並把它對 EVK043027B 的意義講清楚。

## 3. 格式，以及那個檔案

面板播的是 **AVI 容器裡的 Motion JPEG**。每一格都是一張完整的 JPEG，格與格之間
沒有任何互相參照。

這不是妥協，這正是重點。它是唯一一種每格的工作量剛好就是 STM32H7 的 JPEG 硬體在
做的事的常見影片格式；而正因為沒有畫面間預測，播放可以從任何一格開始、可以瞬間
回頭重播，也可以在某一格壞掉時直接跳到下一格。

要做出這樣的檔案：

```bash
ffmpeg -i source.mp4 -vf "scale=800:480,fps=24" -c:v mjpeg -q:v 3 -an intro.avi
```

`-an` 會把聲音丟掉——見[§7](#7-這裡刻意不做的事)。把結果放到 FAT32 或 exFAT 卡片
上的任何位置，再把名字——若在資料夾裡就連資料夾一起——打進元件裡。

### 讀取器走過的那棵 AVI

AVI 是一個 RIFF 檔：一棵由四字元區塊組成的樹，每塊帶一個 32 位元長度，並補齊到
偶數位元組。其中兩根樹枝有意義。

```
RIFF 'AVI '
├── LIST 'hdrl'                   ← 開檔時讀一次
│   ├── 'avih'                    ← 每格間隔、寬、高、總格數
│   └── LIST 'strl'（每個串流一個）
│       └── 'strh'                ← 'vids' + 'MJPG' 指出哪一軌是影像
├── LIST 'movi'                   ← 一次串流一塊
│   ├── '00dc' <jpeg 影格>
│   ├── '01wb' <音訊>             ← 跳過
│   └── ...
└── 'idx1'                        ← 從來不讀
```

讀取器（[`hmi_avi.c`](../../firmware/stm32h747i-disco/src/hmi_avi.c)）只解析
`hdrl` 一次，之後就照檔案順序走 `movi`，每次呼叫回傳一格壓縮影格。**索引完全不
讀。** 串流放棄了跳到任意一格的能力——產品裡沒有任何地方需要它——換來的是一個
記憶體不隨片長增長的讀取器，而且壞掉的索引擋不住它。

Motion JPEG 從來就沒有統一的拼法，所以 `MJPG`、`mjpg`、`MJPA`、`MJPB`、`AVRn`、
`jpeg` 與 `dmb1` 全部接受。它們都是普通的 JPEG 影格，硬體根本分不出差別；為了標籤
怎麼拼而拒絕一個檔案，是一個沒有後果的區別。

## 4. 一格畫面怎麼變成像素

兩個週邊，像素路徑上沒有 CPU：

```
SD 卡 ──f_read──► 壓縮影格 ──JPEG 硬體──► YCbCr，以 MCU 區塊排列
                                                 │
                                               DMA2D
                                                 │
                                                 ▼
                       RGB565，掃描線順序 ──► LTDC 第 1 層 ──► 面板
                                                      ▲
                               LVGL 的畫面 ──► LTDC 第 0 層
```

在這顆晶片上，JPEG 硬體與 DMA2D 是成對設計的：DMA2D 的 YCbCr 輸入模式讀的正是
JPEG 硬體輸出的那種 MCU 區塊排列，轉換之後寫出掃描線順序的 RGB565。這裡沒有
任何「軟體解碼加硬體輔助」——它就是硬體解碼。

**而且影格從頭到尾不經過 LVGL。** 顯示控制器有兩個硬體圖層；LVGL 畫在第一層，解出來
的影格交給第二層，由 LTDC 在送往面板的路上合成在 UI 之上。在這之前，影格是當成圖片
交給 LVGL：CPU 把 1.5 MB 搬進 framebuffer，再複製一次讓第二個 buffer 跟上——每格三
百萬位元組的 SDRAM 流量，光這件事就吃掉大半個影格週期。現在完全沒有東西在複製影格。
代價寫在[§7](#7-這裡刻意不做的事)：這一層永遠在最上面。

兩塊畫面緩衝區輪流使用，所以 DMA2D 寫的是面板**沒有**在掃描的那一塊；交換先排程好，
在垂直消隱時落地，和 LVGL 自己的影格一樣。

兩段都用**輪詢**，而且整件事跑在一個 `lv_timer` 回呼裡。呼叫端本來就得等到那一格
才有東西可以顯示，非同步解碼除了多一台狀態機之外買不到任何東西。

### 時間預算

24 fps 時一格是 41.7 ms。一張 800×480 影格花掉幾毫秒的硬體時間，以及在這裡設定的
約 27 Mbit/s 位元率下大約 140 KB 的卡片讀取。主迴圈在兩格之間照樣跑 Modbus 與觸控。

現在最大的單一成本是**讀卡**，而它對「怎麼讀」非常敏感。一格影格從 muxer 留下的任何
位置開始——任何磁區的任何位元組——而從那裡開始讀，會讓 FatFs 把第一個不完整的磁區
經由自己的緩衝區複製，然後交給卡片一個不再對齊到字組的目的地，而 SD 層對那種目的地
只能一個指令讀一個磁區。`city.avi` 的 1347 格裡有 634 格落在這種位置；每一格要花
約 280 個卡片指令而不是約 5 個，影片就爬了起來。讀取器現在會退到影格之前的磁區邊界、
從那裡讀進字組對齊的緩衝區，所以每個磁區都直接從卡片落到定位。匯流排也改成從 50 MHz
High Speed 起步，第一次讀取失敗就永久降到 25 MHz——見
[§6](#sd-匯流排先快後慢只降一次)。

畫面不縮放——LTDC 做不到——所以它以自己的尺寸顯示，在元件裡置中、裁到元件的框。
**請把 Video 元件設成影片的大小。** 比畫面大的元件四周是黑的；比畫面小的元件顯示
中間那一塊。

### 怎麼量

這份韌體沒有主控台。`hmi_video_stats` 是一個除錯器讀得到的全域變數——暫停後
`p hmi_video_stats`——裡面有上一格的讀取、解碼與顯示時間（微秒）、到目前為止最差的
一格，以及格數。超過週期（24 fps 時 41 667 µs）的都是掉格。

### 那些緩衝區

| 緩衝區 | 800×480 時的大小 | 誰寫 | 誰讀 |
| --- | --- | --- | --- |
| 壓縮影格 | 512 KB | `f_read` | JPEG 硬體 |
| YCbCr MCU 區塊 | 1152 KB | JPEG 硬體 | DMA2D |
| RGB565 畫面 × 2 | 2 × 768 KB | DMA2D | LTDC |

全部放在板子的外部 SDRAM，在 `.sdram` 區段裡，位於 LVGL 自己那 4 MB 堆積之上。
它們是**共用的，不是每個元件一份**，因為同一時間只有一個影片在解碼
（[§5](#5-同一時間只有一個播放器)）。用 RGB565 而不是顯示器其他部分用的 ARGB8888：
LTDC 每秒掃這塊緩衝區六十次，走的是 LVGL framebuffer 也在走的那條 SDRAM 匯流排，
位元組減半就是那份頻寬減半。

沒有 Video 元件的專案一毛都不用付。當沒有任何地方呼叫 `hmi_video_attach` 時，
`--gc-sections` 會把整份執行期與它的緩衝區一起丟掉；在這塊板子上實測，一個帶影片的
畫面比同一個不帶影片的畫面多花 **20 KB Flash 與 3.1 MB SDRAM**，而沒有影片的專案
和這個功能出現之前逐位元組相同。

D-Cache 只在唯一需要的那次交接上維護：硬體輸出是 CPU 寫的，在 DMA2D 讀之前先
clean。轉換好的影格什麼都不用做——DMA2D 寫它、LTDC 讀它，CPU 從頭到尾沒碰。卡片用
輪詢而不是 DMA 讀取，等於在那一側直接繞開同一個問題，代價是本來就在等待的那段 CPU
時間。

## 5. 同一時間只有一個播放器

只有一顆 JPEG 硬體、一組緩衝區，所以執行期會播**已載入畫面上的第一個 Video
元件**，其他的則顯示 *Another video is playing*。一個畫面一部影片才是專案真正的
形狀；跨畫面註冊好幾個是很平常的事，而且可以運作。

專案設定樣式的那個元件，就是那塊黑框。執行期在它裡面放一個子物件——一個置中的
**`lv_label`**，承載面板要說的話——而畫面本身則顯示在覆蓋層上，對準黑框的位置。
標籤繼承黑框的文字顏色，所以訊息是由元件自己的 **Text Color** 那一列決定樣式，
而不是寫死在程式裡。

離開畫面時，覆蓋層會從畫面自己的 unload 事件立刻撤下，而不是等下一次計時器：
一個壓在 LVGL 之上的圖層，否則會被畫在取代它的那個畫面的最上面。

**`ui_init` 時什麼都不開。** `hmi_video_attach` 只記下名字就回來；卡片是在元件真的
出現在使用中畫面上時才第一次被碰。所以使用者從未打開的畫面完全不會存取卡片、開機
不會卡在一張沒插的卡上，而面板啟動之後才插進去的卡也還是找得到。離開畫面會放掉
檔案；回到畫面會從第一格重新打開，這也是失敗的元件重新獲得一次機會的方式。

## 6. 面板會說什麼，什麼時候說

| 元件上顯示 | 發生了什麼 |
| --- | --- |
| **Video not found** | 卡片根目錄沒有那個名字的檔案——或者這個元件根本沒填檔名。 |
| **No SD card** | 插槽裡沒有東西。插槽的偵測腳位這麼說。 |
| **SD card unreadable** | 卡在裡面，但初始化不起來，或上面沒有檔案系統。 |
| **Video format not supported** | 檔案不是 AVI、影像軌不是 Motion JPEG、影格比緩衝區大，或畫面是這條硬體路徑轉換不了的形狀。 |
| **Another video is playing** | 同一畫面上的第二個 Video 元件。見[§5](#5-同一時間只有一個播放器)。 |

這些刻意不合併。對播放器來說，「檔案不見了」和「卡沒插」是同一種失敗；對手上拿著
卡片的人來說完全是兩回事，而在人家只是忘了把卡推進去的時候告訴他影片不見了，會把
他送去錯的地方找。

### 訊息下面那一行

每一則訊息都帶著第二行，說明**是哪一步失敗、它回報了什麼**——`mount failed (FR 13)`、
`read failed (-4) at 8192 x64`、`codec H264 is not MJPEG`、`decode: HAL 3 err 0x4 out 0`、
`4:2:2 612x400 not block-aligned`。標題是給站在面板前面的人看的；細節是給要修它的人
看的。光是一句 *SD card unreadable* 誰都沒辦法據此行動，而一塊只會說這句話的面板，
就是一塊得接上除錯器才看得懂的面板。

代碼是底層自己的：`FR n` 是 FatFs 的 `FRESULT`，單獨的負數是 BSP 錯誤碼，
`HAL n err 0x…` 是 HAL 狀態加上 JPEG handle 的 `ErrorCode`。

### 什麼會重試、什麼不會

失敗依「面板上有沒有任何事能改變它」分成兩類：

| 類別 | 訊息 | 會怎樣 |
| --- | --- | --- |
| **卡片類** | *No SD card*、*SD card unreadable*、*Video not found* | 立刻顯示，**每秒再試一次**。把卡推進去就開始播；把檔案複製到卡上重插就找得到；某一次讀取 CRC 錯誤只損失一格，不會結束整部片。 |
| **檔案類** | *Video format not supported* | 顯示後就放著。面板上沒有任何事能把 H.264 變成 Motion JPEG。離開畫面再回來會重試。 |

### SD 匯流排先快後慢，只降一次

BSP 在卡片初始化的最後會切到 High Speed——`SDMMC_CK` 50 MHz——而且不檢查有沒有
成功。這塊 Discovery 的插槽在離 MCU 最遠的那一側，50 MHz 正是某些卡片偶爾讀取會 CRC
失敗的地方。但它也是兩倍的吞吐量，而一格份量的讀取是顯示一格最大的單一成本。所以
匯流排**從 50 MHz 起步，第一次讀取失敗就永久降到 25 MHz**：在那裡失敗過一次的卡片
還會再失敗，為了查明這件事損失一格，比每隔幾秒就損失一格便宜。

### 在編輯器裡，以及在 Preview 裡

設計畫布、Preview 與 Emulator 都不播任何東西。它們都沒有面板的讀卡機，也從來沒看
過那個檔案。

所以三者都畫出畫面將要佔住的那個框，把檔名寫在上面，而不是憑空捏造一張劇照。
Emulator 會在元件裡寫 *Not played in the Emulator*。在那裡顯示 **Video not found**
會是另一種宣稱——宣稱卡片被看過而且是空的——而只有面板能這樣說。

## 7. 這裡刻意不做的事

**不播聲音。** 執行期會直接跳過音訊串流，不解碼它。一軌 MP3 或 AAC 需要一份解碼
函式庫、把 WM8994 codec 掛上 SAI，還需要一套讓聲音跟著影像時鐘走的緩衝紀律——那是
另一個專案份量的工作，而且目前元件的設定裡沒有任何一項需要它。做檔案時請加 `-an`；
不管有沒有聲音，影格都一樣，音訊串流只是讓檔案變大而已。

**播放中的影片上面畫不了任何東西。** 畫面在顯示控制器的第二層，LTDC 把它合成在
LVGL 畫的一切*之上*。在編輯器裡疊在元件上的標籤，到了面板上會在影片底下。元件旁邊的
一切照舊是 LVGL 的：這一層用逐像素 alpha 混色，而它的預設顏色——LTDC 在視窗外、以及
圖層停用時到處塗的那個顏色——是透明的。換成常數 alpha 混色就不是了，第一版就因此在
視窗沒蓋到的每一塊 UI 上塗了不透明的黑。這是不複製
影格的代價，也是正確的代價：另一條路要花掉大半個影格週期。說明文字放在影片旁邊，不要
放在上面。

**畫面不縮放。** LTDC 做不到，所以 800×480 的影片放進 400×240 的元件，顯示的是中間
的 400×240。請把元件設成影片的大小，或把影片編碼成元件的大小。

**不能跳轉，也沒有播放控制列。** 元件只有 Auto Play 與 Loop。執行期裡有
`hmi_video_play`、`hmi_video_pause` 與 `hmi_video_stop` 可以讓事件或邏輯圖呼叫，但
編輯器還沒有任何動作綁上去。

**畫面必須是整數個 MCU 區塊。** 4:4:4 是 8×8、4:2:2 是 16×8、4:2:0 是 16×16。
區塊排列的來源只有在整除時才跟掃描線目的地對得上；要處理那條參差的邊，就得在每一
格上每個 MCU 列各發一次 DMA2D，只為了救一種沒有人會產出的影片。800×480——面板自己
的尺寸——在三種取樣下都整除。

**灰階與 CMYK 的 JPEG 會被拒絕。** DMA2D 的 YCbCr 輸入模式只涵蓋 4:4:4、4:2:2 與
4:2:0，而那兩種都不是編碼器會為影片產出的東西。

**大於 512 KB 的影格會被拒絕。** 在這裡設定的位元率下一格大約 140 KB，所以這個上限
遠遠超過任何合理的品質設定——而真的超過的檔案會說出來，而不是拿一段被截斷的資料去
解碼。

**檔案內不能跳轉。** 清單可以在檔案之間前進，但不能跳到單一檔案裡的任意位置。

## 10. 這個硬體相依到底有多硬

Video 是整個編輯器裡唯一一個「能不能用」取決於晶片本身的元件。其他每個元件都是
LVGL 用軟體畫出來的，搬到新板子就是寫一份顯示驅動。Video 不是這樣，而它「哪些部分」
不是這樣，值得講精確。

### 10.1 四個層次

| 層次 | 依賴 | 硬性程度 |
| --- | --- | --- |
| **解碼** | JPEG 硬體編解碼器 | **絕對。** 沒有它就沒有影片——見 [§10.2](#102-為什麼沒有軟體退路)。 |
| **色彩轉換** | DMA2D 的 YCbCr 輸入模式 | 原則上絕對，但每顆有 JPEG 硬體的 STM32 也都有它。 |
| **讀檔** | SDMMC 與 microSD 插槽 | 軟性。USB 隨身碟或 QSPI NOR 都行；只需要改 [`hmi_sd.c`](../../firmware/stm32h747i-disco/src/hmi_sd.c)。 |
| **記憶體** | [§4](#那些緩衝區) 那三塊共 3.1 MB 的緩衝區 | 偏硬。需要外部 RAM；沒有哪顆 STM32 的內部 SRAM 能在兩張 framebuffer 和一份 LVGL heap 之外還塞得下這些。 |

哪些晶片有這顆硬體是矽晶片的事實，直接從每顆晶片的 device header 讀出來
（`JPEG_BASE` 有定義就是有，沒定義就是沒有）：

| 晶片 | `JPEG_BASE` | 板上外部 RAM | 結論 |
| --- | --- | --- | --- |
| STM32H747XI（H747I-DISCO） | 有 | 32 MB SDRAM | ✅ 播得動 |
| STM32F746NG（F746G-DISCO） | 無——F76x/F77x 才開始有 | 8 MB SDRAM | ❌ 沒有硬體 |
| STM32U599NJ（EVK043027B） | 無——只有一個同名的 DCMI 擷取模式位元 | 無；內部 SRAM 2496 KB | ❌ 沒有硬體，緩衝區也無處可放 |

U599 確實有 SDMMC1、SDMMC2 與 DMA2D。但都幫不上忙：它缺的那一層正好是沒有替代品的
那一層。

### 10.2 為什麼沒有軟體退路

最自然的問題是：沒有硬體的板子能不能用軟體解碼，慢一點也好？可以，但出來的東西不會是
影片。

一張 800×480 的 baseline JPEG 在 400 MHz 的 Cortex-M7 上用 libjpeg-turbo 或 TJpgDec
解，大約要 150–300 ms——**一秒 3 到 6 格**，而這個格式編碼的是 24 格。而且在那幾百
毫秒裡 CPU 就是解碼器：LVGL 不畫、觸控不讀、Modbus 不輪詢。一個在每張之間把面板凍住
的幻燈片，不是這個功能的慢速版本；它是另一個更糟的功能頂著同一個名字。

降解析度會改變算術，不會改變結論。320×240、10 fps 在 F746 上用軟體做得到，而面板在每
格的大部分時間裡仍然會停住。那是一個真的想要它的產品該做的決定，配上它自己的元件、
自己誠實的名字——而不是偷偷塞在這個元件底下的退路。

所以執行期刻意沒有軟體路徑。缺硬體的板子會說「不能建置」，而不是建出一個在編輯器裡
看起來能用、到了桌上卻一頓一頓的東西。

### 10.3 哪些搬得走，哪些搬不走

實作的大部分都是可攜的。只有一個檔案焊死在那顆晶片上。

| 部分 | 可攜？ | 說明 |
| --- | --- | --- |
| 編輯器：分類、元件、屬性面板、畫布、Prototype、Emulator、程式碼產生 | **完全可攜。** | 除了 `BoardDefinition.video` 之外對板子一無所知。 |
| 建置閘門（Deploy 分頁、Video 區塊） | **可攜。** | 讀的是同一個欄位。新板子就是 [`src/types/hmi.ts`](../../src/types/hmi.ts) 裡的一個條目。 |
| [`hmi_avi.c`](../../firmware/stm32h747i-disco/src/hmi_avi.c)——AVI 解多工 | **可攜。** | 跑在 FatFs 上的純 C。裡面沒有任何週邊。 |
| [`hmi_sd.c`](../../firmware/stm32h747i-disco/src/hmi_sd.c)、[`ffconf.h`](../../firmware/stm32h747i-disco/include/ffconf.h) | 大致可攜。 | `disk_*` 函式呼叫的是板子的 BSP；換儲存裝置就是重寫那五個函式，它們之上的東西不動。 |
| [`hmi_video.c`](../../firmware/stm32h747i-disco/src/hmi_video.c)——元件執行期 | 大致可攜。 | 除了三塊緩衝區上的 `.sdram` 區段屬性之外都是純 LVGL；記憶體配置不同的板子會把它們放在別處。 |
| [`hmi_jpeg.c`](../../firmware/stm32h747i-disco/src/hmi_jpeg.c)——JPEG 硬體 + DMA2D | **不可攜。** | 這個檔案就是硬體本身。搬到 F769 或 H7B3 要重新確認時脈啟用、MCU 區塊幾何與快取維護——在有硬體的晶片上是一天的工作，在沒有的晶片上不可能。 |

所以要新增一塊**有**這顆硬體的板子——F769I-DISCO、H7B3I-DK、或一塊以 H750 為核心的
自製板——工作是：板子定義裡一個 `video` 條目、把四個 `hmi_*` 執行期檔案複製過去並把
`hmi_jpeg.c` 與 `hmi_sd.c` 改指向那塊板子的 BSP、在它的 `bootstrap-deps.ps1` 裡釘上
FatFs，以及在它的 `CMakeLists.txt` 裡加上 HAL 的 JPEG/SD 原始檔。

### 10.4 這對 EVK043027B 的意義

這一段值得直白地講。EVK043027B 是 EDT 自家的評估板，而**這個元件永遠跑不了它**：
STM32U599 沒有 JPEG 硬體，板子也沒有外部 RAM，兩者都不是一份驅動補得上的。放了 Video
元件的專案在它上面不能建置，Deploy 分頁會這麼說。

如果產品線預期在 U599 面板上要有影片，選項是這幾個，而且它們是產品決策而不是工程
決策：

1. **把影片當成 H7 等級板子的功能。** 這是編輯器目前的做法。元件在每塊板子上都能設計；
   在播得動的板子上能建置。
2. **另做一個小一點、名字誠實的元件**——用軟體解碼的 *Slideshow* 或 *Animated Image*，
   320×240、一秒幾格，解碼時 UI 會停住。U599 做得到；但那不是這個元件，也不該當影片
   賣。
3. **下一版硬體換成有這顆硬體的晶片**——STM32H7（H743、H750、H7A3/H7B3）或 F76x/F77x
   ——配外部 SDRAM，或用 H7B3 的 1.4 MB 內部 SRAM 放緩衝區。

三個選項都不需要動編輯器或韌體的任何東西：閘門已經在正確的地方說「不能建置」，而一塊
有了硬體的板子只差一個條目。

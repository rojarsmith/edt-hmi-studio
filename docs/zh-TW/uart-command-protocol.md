# UART 命令協定，以及那個必須管得動它的編輯器

<p align="center">
  <a href="../uart-command-protocol.md">English</a> · <strong>繁體中文</strong>
</p>

狀態：**只有規劃，沒有改任何程式碼。** 內容都對照過原始碼，不是憑印象。

有兩份文件通到這裡。[protocol-and-tags.md](./protocol-and-tags.md) §8 問的是
UART 命令協定能不能*定址*，結論是可以——命令樣板放在連線上，位址放在 tag 上。
[protocol-coexistence.md](./protocol-coexistence.md) 問的是它跟 Modbus 共用一條線
會怎樣，以及那對元件、邏輯與三塊板子各要付什麼代價。這兩份都在講模型。
**這一份講的是作者**：命令的設計要滿足什麼，才值得做；在 Modbus 已經是 tag 形狀的
STM32H747I-DISCO 上它長什麼樣；可不可行；以及 Protocol 分頁要先變成什麼樣子，才可能
被一個手上沒有協定手冊的人用得動。

先給結論，這樣後面可以跳著讀：

- **可行：可以**，而且比看起來小——tag 表不用改，descriptor 只動十三個欄位中的兩個，
  韌體的接縫早就以兩份板子檔案之間的 diff 形式寫好了（§3）。
- **能滿足這個專案核心價值的命令設計**，是「一台裝置只描述一次、一個值只命名一次」，
  而且 tag 層以上永遠不會知道中間有 ASCII 這回事（§1、§2）。
- **圖形化管理：可以，而且它是工作量比較大的那一半**——但其中每一項都會改善今天這個
  只有 Modbus 的畫面，所以沒有任何一項是替一個還沒出貨的協定先付的錢（§4、§5）。

## 1. 把核心價值寫成可以拿來當測試的樣子

README 承諾的是一個視覺化編輯器：不寫程式就產出 LVGL 畫面的 C。把它帶進協定這一層，
就是一句話：

> **作者負責命名值。工具負責處理線上的事。**

這句話可以驗證，所以把它拆成四條測試，拿去套每一個提出來的命令功能：

| | 測試 | 什麼時候算失敗 |
|---|---|---|
| **T1** | tag 層以上沒有人知道協定是什麼 | 元件綁定或邏輯節點得知道這個值是以 ASCII 送來的 |
| **T2** | 一台裝置描述一次，一個值命名一次 | 一台 40 個參數的裝置要手打 40 條命令字串 |
| **T3** | 模型表達不了的東西，要**看得見地**被拒絕 | 一台要先登入的有狀態裝置被硬塞進 tag 表，而不是被導向程式碼出口 |
| **T4** | 作者在板子還沒到之前就看得到它會動 | 想知道命令對不對，唯一的辦法是編譯、燒錄，然後盯著一個空白的元件看 |

T1–T3 在 [protocol-and-tags.md](./protocol-and-tags.md) §8 已經定案，§2 只複述到夠
往下接的程度。

**T4 才是這份文件真正要講的**，而且它是新的。它也是目前 Protocol 分頁敗得最徹底的
一條——重點是，Modbus 讓你敗了也沒事：

| | Modbus RTU | 命令協定 |
|---|---|---|
| 位址寫錯 | 例外碼 02，或逾時。很大聲，而且只有一種意思 | 解析出 `0`、沒有回覆，或者回的是*另一個*參數的值 |
| 框架設錯 | CRC 失敗，client 本來就處理得了 | `GET TEMP\r` 對上 `GET TEMP\r\n`——裝置可能回、可能慢回，也可能回一次之後再也不回 |
| 值的位置抓錯 | 不可能發生；暫存器就是暫存器 | `TEMP=25.4` 對上 `TEMP = 25.4` 對上 `25.4 C`——三種定位方式，每一種都很合理 |
| 大小寫、空白、結束字元 | 不適用 | 每一項都是無聲的失敗 |

Modbus 的位址不是對就是錯，而且錯得看得懂。命令協定有十幾種「差一點就對」的方式，
而每一種從一個空白元件看起來都長得一樣。**沒有即時流量畫面的命令協定就是在猜謎**，
而要一個不寫程式的作者用「編譯－燒錄－瞇眼看」來玩這個猜謎，不能算是產品。

所以 T4 不是第二版再補的加分項。它是讓另外三條值得做的那一條。

## 2. 模型，以及前兩份文件留著沒講明的那一層

先用一張表複述，出自 [protocol-and-tags.md](./protocol-and-tags.md) §8.3 與 §8.5
——這部分已經定案，這裡不再重新論證：

| 屬於誰 | 是什麼 | 為什麼在那裡 |
|---|---|---|
| **連線** | baud、parity、框架／結束字元、checksum、回音抑制、命令間隔 | 兩台裝置共用一條線，這些必須一致 |
| **裝置** | `read` / `write` 樣板：`GET {address}` / `SET {address} {value}` | T2——形狀只打一次 |
| **Tag** | 位址字串（`TEMP`、`40001`、`MEAS:VOLT`），加上值的型別、scale、存取與輪詢間隔 | tag 表在三種協定下都維持**同一張**表 |
| **Tag（例外）** | 單一 tag 的命令覆寫與定位器 | 只裝例外，好讓常規情況維持空白 |

前兩份文件留著沒講明的，是裝置與它的 tag 之間那一層；值得把它命名出來，因為它正是
UI 必須畫出來的東西：

```
連線 ──── 裝置 ──── （命令） ──── Tag
 │          │            │          └── 名稱、型別、scale、存取、輪詢
 │          │            └── 一次請求、一次回覆、N 個定位器
 │          └── 樣板、站號、逾時、重試
 └── baud、框架、checksum、間隔、半雙工
```

**一個「命令」就是一次交換：送出一個東西、預期一份回覆，並從裡面找出一個或多個
值。** 在常規情況下它是隱形的——裝置的樣板加上 tag 的位址*就是*那個命令，作者根本不會
看到這一層。它只在一種情況下現身，而那種情況很常見：

> `STATUS?` → `25.4,60,1,0`

一次請求，四個值。[protocol-and-tags.md](./protocol-and-tags.md) §8.4 已經指出這就是
CAN 那個關係寫成文字的版本——一個訊框載著好幾個訊號；§8.6 也已經指出韌體的 transaction
必須能扇出才服務得了它。

而那個觀察還沒被兌現的紅利是：**編輯器只需要一套「一次請求、多個值」的介面，而它同時
服務 CAN 訊框與文字的批次回覆。** 一個概念，設計一次、測一次、作者學一次，蓋掉兩種
協定。

它同時修掉一件已經做錯的事。今天面板裡的 CAN 區塊，是把訊號畫成**每一列都重複
`Frame ID` 的十二欄平表**（`ProtocolPanel.tsx:925`）。訊框與訊號的關係在資料裡存在，
在 UI 上看不見。用同一種方式做批次回覆的表格，只會把這個錯誤在第二個協定上再犯一次；
做成有分組的版本，則是兩個一起修好。

由此得到三個模型決定，而且都是現在該做的：

1. **「命令」是裝置底下第一級的、可選的、具名的物件。** 樣板驅動的裝置沒有它；批次
   回覆與像 `TARE` 這種沒有位址的一次性動詞則明確有一個。
2. **定位器屬於命令，不屬於連線。** 框架講的是回覆在哪裡*結束*，定位器講的是值在
   哪裡。這是兩個問題，而只有前者是 per-link。
3. **一個 tag 參照一個命令與一個定位器，或者兩個都不參照。** 兩個都不參照就是常規
   情況，而那正是 T2 成立的原因。

## 3. 在 STM32H747I-DISCO 上可行嗎？

可行。一層一層看，配上實際有的東西：

| 層 | 要改什麼 | 規模 |
|---|---|---|
| Tag 表 | **不用改。** 位址欄位改成顯示字串，而不是 area + 數字 | — |
| 元件綁定 | 除了 [protocol-coexistence.md](./protocol-coexistence.md) §4 在只有一個協定時就已經要求的以外，不用再改 | — |
| 邏輯 | 除了該文 §5 那個以 tag 為鍵的執行期 API 以外不用再改——而那本來就會拿掉三個它不該有的拒絕 | — |
| Descriptor ABI | `area` + `address` 換成有標籤的 `source` union：**十三個欄位裡的兩個**（[protocol-and-tags.md](./protocol-and-tags.md) §8.6） | 外科手術等級 |
| 韌體傳輸層 | 已經是 diff，不是設計問題：五個操作，集中在 `modbus_rtu_async_client.c`（[protocol-coexistence.md](./protocol-coexistence.md) §12.4） | 已知 |
| 韌體驅動 | 新的：樣板代入、結束字元掃描、checksum，以及五種定位器 | 真正的工作——幾百行，而且只要 §12.4 的收斂先做，就**只寫一次** |

這裡沒有一項是難的。真正**跟板子有關**、也就是「在 H747I 上」這個問題的老實答案是：

- **那塊板子只有一條連線。** USART1 走 PA9/PA10 經 ST-LINK VCP，沒有別的
  （[protocol-coexistence.md](./protocol-coexistence.md) §12.1）。所以命令裝置在那裡
  不是「多加一台」，而是**共線者**，§3 那六條規則從第一天就全部適用。
- **R5 在這塊板子上是有牙齒的。** 會主動推播的裝置需要一條自己的線，而 H747I 沒有
  第二條線可以給它。在那塊板子上，編輯器的答案必須是拒絕，不是警告。能容納這種裝置的
  是 EDT 板，因為它的 RS-485 埠是一條真正的第二連線
  （[protocol-coexistence.md](./protocol-coexistence.md) §12.2）。
- **預算算式在那裡是字面成立的。** 它是真的 UART、真的 baud rate，所以 §8 的數字照
  原樣適用：一次 Modbus 交換約 25 ms、一次 ASCII 往返約 47 ms、四個 tag 的週期約
  122 ms。也就是說命令裝置在 H747I 上是**要付出看得見的代價**的，而作者應該在選輪詢
  間隔的當下就看到那個代價，不是燒錄之後才看到。
- **記憶體不是問題。** 定位器是靜態表，每條連線一個回覆緩衝也就幾百個位元組，對上
  外部 SDRAM 裡 4 MB 的 LVGL heap。
- **不要去動 Cortex-M4**（[protocol-coexistence.md](./protocol-coexistence.md)
  §12.5）。上面那個週期裡有 122 ms 是在等。

所以：可行，而且 H747I 是個合理的驗證板——但要記得，在一塊只有一條連線的板子上，
每一個命令 tag 都在跟每一個 Modbus tag 搶同一條線，這讓 §5 的連線預算變成這個功能的
一部分，而不是它的後續工作。

## 4. 為什麼現在的 Protocol 分頁管不動這件事

今天這個畫面是兩張欄位卡加一張平表。對「一台 Modbus 裝置加少數幾個暫存器」來說撐得
過去。面對命令協定它會壞，而且壞在哪裡值得逐條列出來，因為每一條都是 §5 的規格。

**它是一張設定表單，不是一個工作區。** 上面每一樣東西都是「要被存起來的值」。沒有
任何東西顯示狀態、流量、後果，或者這些設定到底對不對。

**完全沒有任何驗證。** 已確認：面板只回報服務層級的錯誤——列舉埠失敗、存檔失敗、
埠測試失敗（`ProtocolPanel.tsx:163`、`:253`、`:331`）。沒有任何一個欄位有檢查。兩個
tag 可以同名。位址可以超出該區域的範圍。輪詢間隔可以短到那條線物理上做不到。scale
可以是 `0`，於是每一筆讀值都被無聲地歸零。以上全部都會被接受、存檔、編譯、出貨。

**tag 表不知道誰在用它。** 沒有「被誰使用」這一欄，所以刪掉一個 tag 是一個在別處產生
後果的無聲動作——正是 [protocol-and-tags.md](./protocol-and-tags.md) §1 想用 **LACK**
徽章標出來的那個失敗。

**「Test」並沒有測試那條連線。** 已確認：`HmiService.testPort`
（`server/hmi/service.ts:393`）是靠 `STM32_Programmer_CLI -l uart` 列出埠，然後檢查
選定的名字有沒有出現在輸出裡。它從來沒有打開那個埠，也沒有送出過一個位元組。對一個
什麼都沒接的埠，它一樣回報成功。對 Modbus 來說這只是誤導；對命令協定來說它毫無用處，
因為所有會出錯的事情都發生在埠打開*之後*。

**工具裡任何地方都看不到流量。** 整個流程中，兩個方向、一個位元組都看不到。這就是
T4 的失敗，而且是徹底的失敗。

**平表撐不住。** 八欄、一個 tag 一列，沒有搜尋、沒有排序、沒有分組、沒有多選、沒有
複製、沒有匯入。一台 40 個具名參數的命令裝置正好就是壓垮它的那個案例——而 40 個參數
還算是小裝置。

**位址欄位沒有型別，而且它的意思寫在別的地方。** 欄位裡寫的是 `0`；解釋那個 `0` 等於
holding register 400001 的句子，是*另一張卡*底下的一行文字。換到第二個協定，同一個
欄位得表示參數名稱，而「底下那行字」撐不過這個改變。

以上都不是在說現在這個畫面做錯了。它是在說：這個畫面是為「一台裝置、一個協定、一張短
表」做的，而命令協定正好就是這三個前提同時失效的那個點。

## 5. 它應該變成的樣子

一個三區塊版面，取代現在兩張疊起來的卡：

```
┌ 連線 ──────────┬ Tags ──────────────────────────────────────────────┐
│ ▾ COM  9600 8N1│  搜尋 […]              裝置：[全部 ▾]   + 新增 Tag │
│   ● PLC   mbus │ ┌────────┬────────┬──────────┬──────┬─────┬──────┐ │
│   ● Scale uart │ │ 名稱   │ 裝置   │ 位址     │ 型別 │ 輪詢│ 使用 │ │
│     ▸ STATUS?  │ │ Motor… │ PLC    │ 4x 40001 │ u16  │ 250 │ 3    │ │
│ ▾ RS-485  閒置 │ │ Weight │ Scale  │ WT       │ f32  │ 500 │ 1    │ │
│   （無裝置）   │ │ Tare   │ Scale  │ TARE  ⚠  │ —    │  —  │ 0    │ │
│ ✚ 新增連線     │ └────────┴────────┴──────────┴──────┴─────┴──────┘ │
├────────────────┴────────────────────────────────────────────────────┤
│ 預算  COM ▰▰▰▰▰▰▱▱▱▱ 週期 122 ms / 250 ms · 49 %                    │
├─────────────────────────────────────────────────────────────────────┤
│ 監視器                                          ⏵ 即時   ⧉ 清除     │
│ 19:21:04.118  ⇢ Scale   47 45 54 20 57 54 0D 0A   GET WT␍␊          │
│ 19:21:04.161  ⇠ Scale   57 54 3D 31 32 2E 33 0D…  WT=12.345 → 12.345│
│ 19:21:04.166  ⇢ PLC     01 03 00 00 00 02 C4 0B   讀 40001×2        │
│ 19:21:04.191  ⇠ PLC     01 03 04 …                MotorSpeed = 1450 │
└─────────────────────────────────────────────────────────────────────┘
```

這張草圖裡有六件事是真正的提案：

**1. 連線做成樹狀，而且連線清單由板子推導出來。** 連線 → 裝置 → 命令，狀態標在節點
上。連線清單來自板子定義（[protocol-coexistence.md](./protocol-coexistence.md)
§12.6），所以專案不可能要求一條板子沒有的線，而 EDT 板上的 RS-485 那一列可以老實地
寫「有裝，沒有裝置」。

**2. 整個專案一張 tag 表**，帶裝置欄、搜尋、分組，以及一個 **被誰使用** 的計數，點開
是一個列出相關元件與邏輯節點的小視窗——一次點擊就跳到那個會被弄壞的東西。位址欄依協定
換外觀：Modbus 是區域下拉加數字、UART 是參數名稱、CAN 是訊框加位元窗。同一張表、同樣
的欄位，只有一個欄位換形狀。

**3. 命令組裝器（Command Composer）**，命令協定真正被作者寫出來的地方：

```
裝置：Scale        協定：UART command
讀取  [ GET ][{address}]                     ⌄ 結束字元 CRLF
寫入  [ SET ][{address}][ ][{value}]         ⌄ checksum none
                                             ⌄ 間隔     20 ms
預覽  對象 tag  [ Weight ▾ ]
   送出  47 45 54 20 57 54 0D 0A
         G  E  T  ␣  W  T  ␍  ␊
   ⏵ 試一下        對象  ( ) COM7   (•) 模擬器
   回覆  WT=12.345␍␊
   定位  ( ) 整段  (•) 去頭尾  ( ) 欄位  ( ) 位元組  ( ) 樣式
         前綴 [WT=]  後綴 [ ]         → WT=[12.345]  =  12.345 ✓
```

其中扛住重量的部分：

- **樣板是用「片」組出來的，不是打字打出來的。** `{address}` 與 `{value}` 是作者拖進去
  的標記，所以不可能拼錯。
- **預覽顯示位元組，而且把看不見的字元變成看得見的。** 結束字元、空白與大小寫正是命令
  協定實際失敗的地方（§1），而一行十六進位加上底下標出來的 `␍␊`，在事情走到硬體之前
  就消掉一整類 bug。以我的看法，這一個控制項是整個功能裡「每行程式碼換來的價值」最高
  的一項。
- **定位器階梯是一組對著真實回覆操作的選項**，作者切換階梯時，命中的部分會在字串裡即時
  highlight。這讓 [protocol-and-tags.md](./protocol-and-tags.md) §8.4 的階梯從一份規格
  變成一個試一下就學會的東西——同時讓 regex 那一階留在最後，而且看起來就是最後。
- **「試一下」可以打模擬器，也可以打真的埠。** 選模擬器時它不需要板子、也不需要裝置，
  這正是 T4 能在設計期就滿足、而不是部署後才滿足的關鍵。

**4. 一個有分組的批次回覆／訊框視圖。** 一個帶多個定位器的命令畫成一個父列、tag 排在
它下面，而 CAN 訊框沿用同一套控制項（§2）。那張重複 `Frame ID` 的平表就此消失。

**5. 連線預算長條**，每條連線一個，隨著輪詢間隔改變即時重算
（[protocol-coexistence.md](./protocol-coexistence.md) §8 與 §12.3）。是作者在選的當下
就看得到的算術，不是編譯之後才跳出來的警告。在 CDC 連線上它依傳輸方式計算，而不是拿
baud rate 去乘。

**6. 監視器。** 一次交換一列：時間、方向、裝置、原始位元組、解讀後的意思，以及這個值
落到哪個 tag 上。錯誤——逾時、checksum 不對、定位器沒有命中——就地變成同一串流裡的一
列。它是一個*協定*視圖，不是終端機：它以交換為單位分組，而且標註意義。它不該長出一個
「自由打字送出」的框當主要控制項；那是另一種工具，而把它當主路徑，等於邀請大家回去用
猜的，不是用組裝器。

同一批還值得帶上兩件小事：**每個欄位的就地驗證**，而且把規則寫在旁邊（同名、位址超出
區域範圍、scale ≠ 0、輪詢間隔低於連線做得到的值），以及 tag 表的 **CSV 匯入**，因為
一台 40 個參數的裝置是以 PDF 裡一張表格的形式送來的，不該有人用手打。

## 6. 即時畫面的代價，以及其中唯一那個相依決定

監視器與「試一下」都需要編輯器能打開序列埠，而它今天做不到。已確認：本機 HMI 服務是靠
`STM32_Programmer_CLI -l uart` 列舉埠的（`server/hmi/service.ts:349`），而
`package.json` 裡沒有任何序列埠相依。兩條路：

| | 路線 | 代價 | 後果 |
|---|---|---|---|
| **A** | 在 Node 服務裡加序列埠函式庫 | 是**原生**模組。桌面版的計畫是把後端做成 esbuild bundle 加 `node.exe`（[desktop-installer-packaging.md](./desktop-installer-packaging.md) §2），原生綁定得每個平台各帶一份 | 服務可以無視窗地驅動那個埠——之後做自動化檢查時有用 |
| **B** | 前端用 Web Serial | 後端不用加任何相依；在瀏覽器版與 WebView2 殼裡都能用；使用者從宿主自己的提示視窗授權那個埠 | 埠被前端握著，不是服務。沒有無視窗用法 |

**建議：先做 B。**「試一下」與監視器都是有人在場的作者工具，那正是 Web Serial 的適用
情境，而 B 讓打包文件裡那套安裝程式故事完全不用動。等到真的需要在沒有視窗的情況下用
那個埠，再回頭看 A。

不管走哪條路都有一個實務註記：PC 端的雙協定模擬器
（[protocol-coexistence.md](./protocol-coexistence.md) §9）與編輯器的「試一下」都想要
同一個 COM port，而同一個埠只有一個行程握得住。要嘛讓模擬器多開一組虛擬埠對，要嘛讓
「試一下」透過模擬器自己的通道去問，而不是走那條線。後者比較簡單，也是上面那張草圖
預設的做法。

## 7. 動手順序

對應到 [protocol-coexistence.md](./protocol-coexistence.md) §10 的階段，好讓兩份規劃
維持成同一份規劃：

| 編輯器工作 | 屬於哪個階段 | 需要硬體嗎？ | 只有 Modbus 時就有用嗎？ |
|---|---|---|---|
| 每個欄位的就地驗證 | 0 | 不用 | **有用** |
| 有型別的位址欄；把說明從卡片底部搬進欄位裡 | 0 | 不用 | **有用** |
| tag 表：搜尋、排序、分組、**被誰使用**、CSV 匯入 | 0–2 | 不用 | **有用** |
| 連線樹，連線由板子推導 | 1 | 不用 | 有用 |
| 監視器 +「試一下」（打模擬器） | 1–2 | 不用 | **有用** |
| 連線預算長條 | 2 | 不用 | **有用** |
| 有分組的訊框／批次視圖；CAN 訊號改用它 | 2 | 不用 | 有用（順便修好今天的 CAN） |
| 命令組裝器，含位元組預覽與定位器階梯 | 5 | 不用——用模擬器 | 沒有 |
| 把「Test」改名／修成真正的連線檢查 | 0 | 不用 | **有用** |

十列裡有九列不需要硬體，七列在只有一個協定的今天就會改善畫面。這就是「編輯器改版是不是
在替未來先付錢」的答案：不是，而且它應該在第二個協定之前開始，不是跟它並行。

## 8. 現在該決定什麼，什麼先別決定

**現在就決定：**

- **「命令」是裝置與 tag 之間第一級的可選物件**，而且在 UI 上與 CAN 訊框共用（§2）。
  這件事晚決定，代價就是兩套「一次請求、多個值」的介面，而不是一套。
- **組裝器預覽位元組，而且把看不見的字元顯示出來**（§5）。它很小，卻消掉了那個讓命令
  協定變難的失敗模式。
- **定位器階梯是結構化優先、regex 最後**，而且 UI 必須讓最後那一階「感覺就是最後」
  （[protocol-and-tags.md](./protocol-and-tags.md) §8.4）。
- **即時流量是功能的一部分，不是後續工作**（T4）。沒有它的命令協定，對這個工具設定的
  使用者來說就是不能用。

**先別決定：**

- 定位器的詞彙，以及框架與 checksum 的選項清單——對著一台真實存在的裝置寫
  （[protocol-and-tags.md](./protocol-and-tags.md) §8.8）。
- Web Serial 還是原生序列模組（§6）。先讓監視器對著模擬器出貨，讓需求自己證明自己。
- 一台裝置可以有幾個命令，以及命令能不能重新排序。

**不要做：**

- **不要在每個 tag 上放命令字串。** 那會打破 T2，也讓一台 40 個參數的裝置變成 40 次
  打錯動詞的機會。
- **不要讓監視器變成終端機。** 把自由輸入的送出框當主要控制項，等於把「寫命令」變回猜
  的——而那正是組裝器存在要終結的事。
- **不要在四個結構化階梯還沒對真實裝置試過之前，就先加一個只有 regex 作者看得懂的
  階梯。**
- **不要把有狀態的裝置硬塞進 tag 表。** 「先登入再讀」是寫明的極限，答案是產生出來的
  程式碼出口（[protocol-and-tags.md](./protocol-and-tags.md) §8.7），而把這件事講明白
  就是 T3。

# Work 頁簽

<p align="center">
  <a href="../work-progress.md">English</a> · <strong>繁體中文</strong>
</p>

這個 session 啟動過的每一個長時間操作，最新的在最上面，放在下方抽屜的第一個頁簽。模型是
Eclipse 的 Progress view，而**跟它不一樣的地方才是重點**。內容都對照過原始碼，不是憑印象。

## 1. 它是為了什麼

旁邊那兩個 log 頁簽回答的是*它說了什麼*。Work 回答的是 log 回答不了的三件事：

- **現在有什麼在跑，跑到哪了？**
- **這個 session 之前跑過什麼，各自怎麼結束的？**
- **這一個可以停掉嗎？**

第二件就是跟 Eclipse 的差別。在那裡，做完的工作會從清單裡被掃掉；在這裡，做完的項目會
一直留到程式關閉為止。「二十分鐘前那次建置到底說了什麼」不該需要再跑一次才回答得出來。

這份歷史是**只在記憶體、永不持久化**的，跟 `factoryDevMode` 的選擇一樣：它講的是這一次
坐下來做的事，不是這個專案的事。

## 2. 一列長什麼樣

```
 #   時間      名稱              進度                 動作
┌──────────────────────────────────────────────────────────────┐
│ 2  23:33:20  Build Firmware   ▓▓▓▓▓▓▓▓▓▓ 585/585      ✓      │
│              Firmware build complete, buildId: 9c887a5b…     │
│ 1  23:32:25  Build Firmware   ▓▓▓▓▓▓▓░░░ 458/585      ⊘      │
│              Firmware build stopped.                         │
└──────────────────────────────────────────────────────────────┘
```

欄位就是指定的那些——id 從 1 開始、時間、名稱、進度條，以及一個沒有標題、裝著停止鈕或
結果符號的欄位。另外多加了三樣，每一樣都是因為「只有表格」會留下一個沒被回答的問題：

- **每一列底下的細節行。** Eclipse 那個視圖最有資訊量的部分就是它的副標，而在這裡它幾乎
  不用成本：跑的時候是最新的一行輸出，結束之後是它怎麼結束的。
- **顯示經過時間，而不是第二個時鐘。** 結束的列寫 *Finished in 45s*，還在跑的往上數。
  起始時間回答的是「那是哪一次」，經過時間回答的是「我還要等多久」——後者才是真正被問的
  那個問題。
- **用 grid 而不是 `<table>`。** 每一列底下都掛著那條細節行，用表格做就得再開一個 `<tr>`
  並且永遠跟上面那個保持同步。欄位一樣是對齊的，而那本來就是表格存在的理由。

## 3. 進度：能確定就確定，不能確定就誠實

Ninja 自己會數它的工作——`[263/585] Building C object …`——而那一行本來就在串流裡經過
（[streaming-build-log.md](./streaming-build-log.md)）。所以進度條是從 log 把數字讀回來
的，不需要建置系統配合任何事：

| 階段 | 進度條 |
|---|---|
| CMake 設定中、相依下載中 | **不確定**——一道掃光，不宣稱任何它不知道的比例 |
| 編譯中 | **確定**，來自 `[N/M]` |
| 成功結束 | 填滿 |
| 被停掉或失敗 | **停在它停下來的地方**——一個死在 458/585 的建置就該一直寫著 458/585 |

最後那一列是刻意的。**失敗時把進度條拉滿，等於告訴讀者跟事實相反的事。**

燒錄沒有計數，全程都是不確定。

## 4. 停止鈕，以及為什麼它是 per item

規格寫的是*要是允許*，而這個條件性馬上就賺到了，因為這兩個操作本質不同：

| | 可以停嗎 | 為什麼 |
|---|---|---|
| **Build Firmware** | **可以** | 它寫的是暫存目錄。砍掉它只賠掉這次建置，沒有別的 |
| **Flash & Reset** | **不行** | 它寫的是板子。**寫到一半的映像檔比一個慢的映像檔更糟** |

所以那個欄位只在「正在跑」**而且**「自稱可取消」時顯示停止鈕；其他情況顯示結果符號——
`✓` 完成、`✕` 失敗、`⊘` 已停止，以及不可取消時的轉圈。

而且取消是真的，不是裝飾。整條鏈都得做出來：

```
work 列的停止鈕
  → deployStore 的 cancel handle
  → POST /api/hmi/build-cancel/:runId
  → HmiService.cancelBuild  → 那次 run 的 AbortController
  → runExecutable 的 signal → child.kill()
```

`runExecutable` 在原本的 `onLine` 旁邊多了一個 `signal` 選項，而且**只有串流路徑理它**
——批次那些呼叫者夠短，根本沒有東西好中斷。負責路由的 run id 就是 log 串流已經在用的
那一個，所以取消沒有多花一個身分。

**建置結束之後才送到的取消不是錯誤**：端點回報 `cancelled: false`，前端忽略它。那是
前端輸掉的一場賽跑，不是故障。

## 5. 抽屜在哪，以及那顆燈

抽屜在**每一個大功能**都在。Work 列的是「活得比啟動它的那個分頁還久」的操作——建置會在
作者去畫畫面的時候繼續跑——所以把它藏在某些分頁，等於把那個唯一不屬於任何分頁的視圖藏
起來。展開與否**只由作者決定**，用右側的箭頭；除了 Deploy 卡片上那兩顆按鈕會在被按下時
把自己的輸出帶到前面以外，沒有任何東西會自動開關它。

也正因為抽屜可以在任何分頁上收著，它需要一個訊號：**只要有任何東西在跑，頁簽列右側就有
一顆紅燈**，沒有東西在跑時它消失。它是**呼吸**而不是閃爍——閃爍是在要求注意，而一個兩
分鐘的建置不該要求兩分鐘的注意——並且在 tooltip 裡帶著正在跑的是誰。它取代了原本每個
頁簽各一個的標記：那個做法把同一件事說了三遍，而且收起來的時候什麼都沒說。

## 6. 實測

兩次執行，全程都在 **Design 分頁**上觀看，用來證明抽屜不屬於任何分頁：

| id | 時間 | 狀態 | 計數 | 進度條 | 符號 | title | 細節 |
|---|---|---|---|---|---|---|---|
| 2 | 23:33:20 | succeeded | 585/585 | 100 % | `✓` | Finished in 45s | `Firmware build complete, buildId: 9c887a5b…` |
| 1 | 23:32:25 | cancelled | 458/585 | 78 % | `⊘` | Stopped in 29s | `Firmware build stopped.` |

第 1 項是手動在 458/585 停掉的，而編譯器**真的停止計數了**；第 2 項在那之後跑到完成。
紅燈在兩次執行期間都亮著，在兩次之間與之後都不在。主控台沒有錯誤。

## 7. 留給以後

- **工廠模式。** 那兩個 log 頁簽是被藏進去的候選，留下 Work 當日常視圖。這裡的東西對兩種
  結果都沒有預設立場。
- **點一列。** 目前點一列不會打開它產生的那份 log。要做對，得讓每一次 run 擁有自己的
  log，而不是由頁簽只保留最新的那一份——那是比這次更大的改動。
- **更多生產者。** 一個新的操作只需要 `useWorkStore.start(name, { cancellable })`；
  這個頁簽裡沒有任何東西專門知道建置或燒錄。

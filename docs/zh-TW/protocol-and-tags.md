# Protocol、Tag，以及切換之後什麼還在——分析

<p align="center">
  <a href="../protocol-and-tags.md">English</a> · <strong>繁體中文</strong>
</p>

狀態：**只有分析，沒有實作。** 這份文件記錄目前程式碼的實際行為、回答被問到的三個
問題，並列出真要改的話該改什麼、以什麼順序。

依提問順序，問題有這些：

1. 讓專案在建立之後還能修改 **Protocol**，是好設計嗎？（§2、§3）
2. 切換的時候，**通訊 TAG** 會不會亂掉？（§3）
3. 之後若要支援第三種協定——特別是**自訂的 UART 串口命令架構**，那既不是 Modbus
   也不是 CAN 的形狀——會發生什麼事？（§4）
4. 這種命令型協定，到底能不能設計成**可定址**？（§8）
5. 目前的抽象能**同時撐住三種**嗎？（§9）
6. 抽象放在編輯器、韌體維持原生，這樣對嗎——以及成熟的 HMI 大廠實務上到底怎麼做？
   （§10）

如果只讀一節，請讀 **§10**：那裡有一個會改變上面所有答案形狀的想法。

## 1. 目前程式碼實際怎麼做

以下都對照過原始碼，不是憑印象。

| 項目 | 位置 | 行為 |
|---|---|---|
| 協定 | `ProjectConfig.protocol`（`src/store/projectStore.ts`） | 一個專案一個。建立專案時從該板子支援的清單挑選，之後可在 Protocol 分頁隨時改 |
| Modbus 設定 | `ProjectConfig.communication` | 串列參數，以及整張 tag 表 |
| CAN 設定 | `ProjectConfig.canBus` | 位元時序，以及 signal 表 |
| 切換動作 | `selectProtocol`（`ProtocolPanel.tsx`） | 只寫入 `protocol`，其他什麼都不動。**不會動到任何 tag、binding 或 signal** |
| 建置閘門 | `DeployPanel.tsx` — `buildable = protocolDefinition.implemented` | CAN 是 `implemented: false`，所以 CAN 專案無法建置 |
| 匯出／匯入 | `exportProject` / `importProject`（`projectStore.ts`）、`migrateProject`（`projectManager.ts`） | 三個欄位在 `.json` 來回一趟後都還在 |

兩份協定設定是**並排保存、而不是互相取代**，型別註解本身就寫明了：

> 專案驅動哪一種現場匯流排，在建立專案時從該板子支援的集合中選定。下面各協定的
> 設定是並排保存而不是取代，所以來回切換不會把使用者已經建好的 tag 表丟掉。

### 兩種「指向 tag」的方式

第二個問題的答案就在這裡。專案裡有兩種消費者，而它們參照 tag 的方式不一樣：

| 消費者 | 存了什麼 | 產生的 C 讀什麼 | tag 被刪掉時 |
|---|---|---|---|
| **元件** — `component.modbusBinding` | `tagId` **加上一整份快照**：area、address、資料型別、存取、scale、輪詢間隔 | **快照**（`hmiBindingGenerator.ts`） | 清掉 `tagId`，快照留著。元件繼續輪詢同一個位址，而且無聲無息 |
| **邏輯節點** — Read Tag／Write Tag | `tagId`（以及只用於顯示的 `tagName`） | **tag 本身**（`ui_logic.c.ts`） | 產生註解、不產生呼叫：`/* tag X no longer exists */` |

兩種各自都說得通。但放在一起，就是同一個專案對同一個問題——*這個 tag 被刪掉會怎樣*
——給了兩種不同的答案。

`synchronizeModbusBindings`（`src/utils/modbusBindings.ts`）負責讓元件的快照保持
最新：tag 表一被編輯，每個綁定的元件都會依 tag 重寫一次，而且走 undo 堆疊。所以
快照只有一種情況會過期——那個 tag 不見了。

## 2. 可以修改 Protocol 是好設計嗎？

**是，而且讓它安全的那一半已經做對了。** 兩個性質撐起這件事：

- **切換不具破壞性。** Modbus tag 與 CAN signal 存在不同欄位，所以切到 CAN 再切
  回來，專案跟原來一模一樣。若非如此，這個下拉選單就是個陷阱：點錯一次，整張 tag
  表就沒了。
- **一個專案一個協定，而不是一個 tag 一個協定。** 板子上只有一條匯流排。混協定的
  tag 表會需要在每個 tag、每個 binding、每份產生的描述子上都掛一個協定判別欄位，
  只為了表達這裡的硬體做不到的事。

**缺的不是節制，而是告知。** 目前的切換什麼都不說，但它可能擱置一大堆東西：

- 每一個 `modbusBinding` 指向 Modbus 表的元件，
- 每一張邏輯圖裡的每一個 Read Tag／Write Tag 節點，
- 以及——若被切走的正是那個已實作的協定——整個建置能力。

Protocol 分頁本來就會講這種話：CAN 那邊會印出「尚無韌體支援」的提示。**在切換發生
之前先數一數會擱置什麼**，是這整頁上最小、也最有用的一個改動。

還有一個範圍更窄的缺陷也屬於這裡。`server/hmi/projectSource.ts` 呼叫
`generateHmiBindings(screens, communication, …)` 時**完全沒有看
`projectFile.protocol`**，所以它會很樂意為一個 CAN 專案吐出 Modbus 描述子。擋在
中間的只有 Deploy 按鈕。等第二個協定變成可建置的那天，這個順序必須反過來：由產碼器
依專案的協定決定，UI 只是反映它。

## 3. TAG 會亂掉嗎？

逐個情境來看：

| 情境 | 實際發生的事 | 判定 |
|---|---|---|
| 切走協定再切回來 | 兩張表都原封不動 | ✅ 安全 |
| 有元件綁著時修改 tag 的位址 | 一次推送到每個綁定的元件，而且可 undo | ✅ 安全 |
| 幫 tag 改名 | binding 參照的是 id，不會斷 | ✅ 安全 |
| 刪掉一個被綁定的 tag | 元件：清掉 `tagId`，繼續輪詢舊位址，沒有任何提示。邏輯節點：拒絕產碼並說明 | ⚠️ **不一致** |
| 切到一個表是空的協定 | 元件 binding 與 tag 節點仍指向舊表，沒有任何提示 | ⚠️ **無聲** |
| 匯出成 `.json` 再打開 | 協定、Modbus 設定、CAN 設定都還在 | ✅ 安全 |

**所以把 tag 弄亂的不是協定選單。** 真正的兩個風險是「刪除時的不一致」與「切換時的
沉默」，而這兩件事都不是「允許修改協定」造成的。

其中讀起來最糟的那一項值得多說一句。元件繼續輪詢一個已刪除 tag 的位址，未必是錯的
——位址還是位址，「解除 tag 綁定但繼續運作」是一種合理解讀。真正的問題在於：元件身
上沒有任何地方說「這個參照被拿掉了」。而這個專案早就有處理這種情況的語彙：動畫在目
標消失時掛的那個紫色 **LACK** 標籤——標示出來，絕不自作主張修好。tag 消失的 binding
應該掛同一個標籤。

## 4. 第三種協定：UART 命令架構

這才是決定形狀的問題，因為命令型協定跟前兩種**不是同一類東西**。

Modbus 與 CAN 都是**可定址**模型。一個 tag 回答三個問題：值在*哪裡*（`area` +
`address`；`frameId` + 位元視窗）、它*是什麼*（資料型別、scale）、以及*多久問一次*
（輪詢間隔）。正因為兩者形狀相同，[邏輯節點分類法的 Decision 1](./logic-node-taxonomy.md)
才成立：圖上寫 `MotorSpeed`，由 Protocol 分頁決定那是 holding register 40001 還是
CAN `0x123.rpm`。

而以行為單位的 UART 命令協定，*不是用同一種方式*可定址的。它長這樣：

```
> GET TEMP\r\n
< TEMP=25.4\r\n
> SET TEMP 30\r\n
< OK\r\n
```

其中有三件事，在今天的 tag 裡沒有位置：

1. **沒有位址。** 有的是一個命令字串，有時還要把參數代進去。
2. **讀和寫是不同的命令**，而不是同一個位址配不同的存取模式。
3. **回覆需要解析**——前綴、分隔符號、第幾個欄位、單位後綴。今天沒有任何欄位能表達
   這件事。

這些都不代表它*不能*可定址，只代表它不會自動就可定址。[§8](#8-uart-命令協定能設計成可定址嗎)
把「要付出什麼才做得到」算了一遍，結論是大多數這類協定都可以——關鍵在一個決定：命令的
形狀放在哪一層。

### 兩種形狀，該預留哪一種

**形狀 A——一張 Tags 表，來源依協定而異。** tag 保留它與協定無關的那一半（名稱、
資料型別、存取、scale、輪詢間隔），而「在哪裡」變成一個帶判別的酬載：

```ts
type TagSource =
  | { kind: 'modbus'; area: ModbusRegisterArea; address: number }
  | { kind: 'can'; frameId: number; startBit: number; bitLength: number; byteOrder: CanByteOrder }
  | { kind: 'uart'; readCommand?: string; writeCommand?: string; parse: ReplyParse };
```

下游全部照舊：元件綁 tag、Read Tag 與 Write Tag 仍是唯二的節點、輪詢迴圈還是輪詢
迴圈。它同時把現在的兩張表併成一張，於是那個現行設計答不出來的問題——*我切換之後
binding 會怎樣？*——變成*哪些 tag 有我切過去那個協定的來源？*，而後者是看得見答案的。

**形狀 B——另開一張 Commands 表。** 對於那些「動詞根本不是值」的協定更貼切：
`REBOOT`、`TARE`、`START CYCLE`。沒有東西可讀回來，也沒有東西要輪詢。但它會讓每一
個消費者分岔——第二套 binding 編輯器、多兩個邏輯節點、第二份產生的描述子表。

**建議：預留形狀 A，只有在「一次性動詞」真的重要時才動用 B。** 一個背後沒有值的動詞
可以表達成「唯寫、且寫入固定值」的 tag，而那跟現在的 `writeBehavior: 'set'` 已經很
接近。把模型翻倍之前，這個值得先試。

### 絕對不能發生的事

目前命名鋪出來的軌跡是：Modbus 用 `communication`、CAN 用 `canBus`，第三個就
`uartCommands`——三個頂層欄位；而在元件那側是 `modbusBinding` 加 `canBinding` 加
`uartBinding`。之後每個屬性編輯器、每個產碼器、每次遷移都要三向分岔，而一個專案的
binding 會默默地屬於「協定當時剛好落在哪個欄位」。

**元件那一側，就是從來沒有套用 Decision 1 的那一半。** 邏輯圖已經跟協定脫鉤了，元件
binding 沒有。`component.modbusBinding` 從名字、型別到欄位都是 Modbus，而且它才是韌
體真正編進去的東西。

## 5. 各項改動的代價

| 改動 | 波及範圍 | 說明 |
|---|---|---|
| 切換前先說會擱置什麼 | 只有 Protocol 分頁 | 數 binding 與 tag 節點；不動模型 |
| tag 消失的 binding 掛 LACK 標籤 | 屬性編輯器 | 這個模式已經存在 |
| 產碼器依專案協定設閘門 | `server/hmi/projectSource.ts` | 一個條件式 |
| `modbusBinding` → `busBinding`，改成帶判別 | **6 個非測試檔**（`types/index.ts`、`utils/modbusBindings.ts`、`codegen/hmiBindingGenerator.ts`、`PropertyEditor.tsx`、`ModbusBindingEditor.tsx`、`store/editorStore.ts`） | 舊專案照讀舊欄位，就是這個 repo 對 `pages`、`targetPage`、巢狀動畫用過的遷移模式 |
| 一張 Tags 表，來源依協定而異 | 上述再加 Protocol 分頁與邏輯的 tag 節點 | 值得**跟 UART 一起做**，而不是提前做 |
| 只把選定協定的 runtime 編進韌體 | 韌體 CMake | 今天每次建置都會連進 `modbus_rtu_client.c`；多一套堆疊之後這就變成尺寸問題 |

## 6. 建議順序

1. **把切換的代價講出來。** 改協定之前，說明有多少元件 binding 與 tag 節點指向即將
   被留下的那張表。
2. **幫 tag 已消失的 binding 掛標籤**，讓元件那側對「刪除」的回答，跟邏輯那側一致。
3. **產碼器依專案協定設閘門**，別讓 UI 是唯一擋住錯誤建置的東西。
4. **把元件 binding 改名成與協定無關的名字**，趁第三個協定還沒把這次改名變成三向
   分岔之前。
5. **UART 模型最後再設計**，手上要有真實裝置的命令集。要預留的是上面的形狀 A，但
   解析規則應該對著一個存在的協定寫，而不是對著想像中的。

第 1–3 項各自獨立、規模都小，而且不管第三個協定會不會來都值得做。第 4 項是唯一有
時限的：今天很便宜，等到有兩個協定同時參照同一個欄位就貴了。

## 7. 刻意不建議的

- **一個 tag 一個協定。** 一塊板子一條匯流排；在每個 tag 上掛判別欄位，是為了表達
  硬體做不到的事。
- **切換時清掉另一個協定的設定。** 現在這個不具破壞性的行為，正是讓這個選單安全的
  性質。
- **把元件 binding 改成純參照。** 那份快照就是韌體要編進描述子表的東西，不是為了
  重複而重複。要修的是幫它取一個與協定無關的名字，而不是把它拿掉。
- **有 binding 就禁止切換。** 把專案改指向新裝置是完全正當的行為。告訴作者代價，
  但不要替他做決定。

## 8. UART 命令協定能設計成可定址嗎？

簡答：**大多數都可以——做法是把命令的形狀往上移到連線層，tag 上只留一個位址。**

### 8.1 「可定址」真正需要的是什麼

不是一個數字。一個 tag 之所以可定址，是因為它帶著一把穩定的鑰匙，能回答兩個問題：
**怎麼問**，以及**答案在回覆的哪裡**。用這個尺度看，三種協定是同一個形狀：

| | 怎麼問 | 答案在哪裡 |
|---|---|---|
| **Modbus** | 功能碼，由 area 隱含 | `address` 上的那個暫存器 |
| **CAN** | 不用問——frame 自己會來 | `frameId` + 位元視窗 |
| **UART** | 一行命令 | 回覆中的某個位置 |

CAN 已經證明這個模型**必須允許「根本不發請求」**：一個只收不問、鑰匙純粹是定位器的
tag。而同一個容許度，剛好也涵蓋了「裝置主動推送」的 UART——否則那是最難塞進來的情況。

### 8.2 哪些命令協定塞得進來

| 型態 | 例子 | 可定址？ | 鑰匙是什麼 |
|---|---|---|---|
| ASCII 暫存器 | `RD 40001` / `WR 40001 25` | 可以，直接就是 | 暫存器編號 |
| 具名參數 | `GET TEMP` / `SET TEMP 30` | 可以 | 參數名稱 |
| SCPI 類 | `MEAS:VOLT?` | 可以 | 節點路徑 |
| 整包回覆 | `STATUS?` → `25.4,60,1,0` | 可以——這就是文字版的 CAN | (命令, 欄位索引) |
| 二進位框架 | `STX 03 … ETX` | 可以 | (命令位元組, 位移+長度) |
| 一次性動詞 | `TARE`、`REBOOT` | 那不是值——用唯寫 tag 表達 | 動詞本身 |
| 主動推送 | 裝置自己送 `TEMP=25.4` | 解碼可以，輪詢不行 | (比對樣式, 欄位) |
| **有狀態的連線階段** | 先登入、切模式，才能讀 | **不行** | 那需要腳本，不是表格 |

最後一列是誠實的邊界，值得講白：一個「命令的意義取決於前面送過什麼」的協定，不是一張
彼此獨立的 tag 表，而且再加多少欄位都不會變成。那種情況需要 §8.7 的逃生口，而工具應該
直說，而不是硬凹。

### 8.3 設計核心：命令往上、位址往下

最直覺的第一版——每個 tag 自己帶一條命令字串——會讓暫存器型裝置無法使用：`RD 40001`、
`RD 40002`、`RD 40003`，要打一百次，每一次都有打錯動詞的機會。

把**形狀**放在連線上，把**位址**放在 tag 上：

| 連線樣板 | tag 的位址 | 產生 |
|---|---|---|
| `RD {address}` / `WR {address} {value}` | `40001` | `RD 40001` |
| `GET {address}` / `SET {address} {value}` | `TEMP` | `GET TEMP` |
| `{address}?` / `{address} {value}` | `MEAS:VOLT` | `MEAS:VOLT?` |

這樣一來，tag 表在**三種協定下長得一模一樣**——名稱、在哪裡、型別、scale、輪詢間隔
——只有「在哪裡」這一欄的意義不同。這就是讓 UART tag 跟 Modbus tag 一樣可定址的關鍵，
也是讓同一套元件 binding、同一個 Read Tag 節點、同一個輪詢迴圈能服務三種協定的關鍵。

```ts
type TagSource =
  | { kind: 'modbus'; area: ModbusRegisterArea; address: number }
  | { kind: 'can'; frameId: number; startBit: number; bitLength: number; byteOrder: CanByteOrder }
  | { kind: 'uart';
      /** 代入連線的樣板。 */
      address: string;
      /** 逐 tag 覆寫，給樣板套不上的那些。 */
      readCommand?: string;
      writeCommand?: string;
      locate?: ReplyLocator;
    };
```

覆寫欄位承載例外：多個 tag 共用的整包回覆、沒有位址的一次性動詞、一台原本規則的裝置上
某個拼法特殊的命令。**規則的情況完全不需要逐 tag 命令。**

### 8.4 答案在哪裡：定位器的階梯

no-code 工具應該照順序提供這些，遇到第一個合用的就停：

| 定位器 | 適用 | 例子 |
|---|---|---|
| **整個回覆** | 回覆本身就是值 | `25.4` |
| **去頭去尾** | 帶標籤的值 | `TEMP=25.4`，前綴 `TEMP=` |
| **欄位** | 有分隔符的紀錄 | `25.4,60,1`，分隔 `,`，索引 0 |
| **位元組** | 二進位框架 | 位移 3、長度 2、big-endian |
| **樣式比對** | 其他一切 | 一個帶單一捕獲群組的 regex |

前四種是作者不需要知道 regex 是什麼也填得出來的結構化欄位。第五種是逃生口：放在最後、
標明它是逃生口，而且不要讓它變成「前四種本來就能處理的協定」的預設答案。

**一個整包回覆，就是一個請求配好幾個定位器**——跟 CAN 的 frame 與 signal 是同一種關係。
這不是要教作者一個新概念，這就是 CAN 已經帶進來的那個概念，換成文字寫法。

### 8.5 哪些東西屬於連線、而不屬於 tag

把這條界線畫對，才不會讓 tag 表每遇到一種裝置怪癖就長出一欄。以下都是「每條連線一份」，
應該放在鮑率旁邊：

- **框架（framing）**——一則回覆怎麼結束：行結束符、固定長度、STX/ETX，或閒置間隔。
  沒有它，runtime 分不出「完整的回覆」與「還沒收完」，其他一切都免談。
- **檢查碼**——無、XOR、sum、CRC-16；收到時驗證、送出時附加。
- **回音抑制**——半雙工線路會把送出去的東西原樣送回來。
- **命令間隔**——有些裝置需要在下一個請求之前留一段空檔。
- **命令樣板**——見 §8.3。

這些沒有一項是「每個值一份」的，而一張把它們扛在身上的 tag 表，意味著同一台裝置上每個
tag 都要重填一次。

### 8.6 韌體已經有的，與還缺的

產生出來的描述子**已經大致與協定無關**。十三個欄位裡，只有兩個是 Modbus：

| 關注點 | 欄位 | 與協定綁定？ |
|---|---|---|
| 值在哪裡 | `area`、`address` | **是——就這兩個** |
| 值是什麼 | `data_type`、`access`、`scale`、`poll_ms` | 否 |
| 它驅動什麼 | `object`、`widget`、`property`、`write_behavior`、`write_value`、`value_reader`、`value_writer` | 否 |

連標頭裡唯一那句 Modbus 的話都只存在於註解：*"Addresses are zero-based Modbus PDU
addresses."* 把那兩個欄位換成一個帶判別的 `source` union，是對 ABI 的外科手術，不是重寫。

runtime 的進度也比預期好：`hmi_runtime.c` 已經有帶種類、重試次數與逾時的**交易
（transaction）**，以及一個在 binding 之間輪轉的輪詢游標。缺的是三件事：

1. **一筆交易只服務一個 binding。** `hmi_transaction_t` 只握著單一個
   `hmi_binding_state_t *`。整包回覆是「一次來回更新好幾個 tag」，所以交易必須能扇出。
2. **傳輸層是一個具體的全域變數。** `static modbus_rtu_async_client_t g_modbus_client;`
   ——第二個協定需要在這裡有一層介面，或者第二套 runtime。
3. **元件描述子是「每個 binding 一份」，不是「每個 tag 一份」。** 三個元件顯示同一個
   tag，就會產生三份描述子、三次來回。邏輯那側已經去重了：
   `collectLogicHoldingRegisterAddresses` 收進一個 `Set`。

第 3 點在命令型協定底下會變質。Modbus RTU 在 9600 下讀一次是幾毫秒；一個 ASCII 請求
加回覆、再加上命令間隔，是數十毫秒。三個元件共用一個 tag、250 ms 輪詢，於是從「浪費」
變成「做不到」。**合併請求不再是最佳化，而是必要條件**，而最自然的合併單位就是 tag
——這也是「元件應該參照 tag 而不是自己扛一份快照」（§1）的另一個理由。

### 8.7 逃生口，以及什麼時候該用它

對於表格表達不了的協定——登入交握、會改變後續命令意義的模式切換、長度前綴的可變紀錄
——誠實的答案是「產生一個掛鉤」，而不是再加一欄。產碼器本來就會輸出能在重新產生時存活
的 `USER_CODE_START` / `USER_CODE_END` 標記；UART 傳輸層可以露出同樣的接縫：*這是剛收到
的一行，這是把值放進去的地方*。

一個會說「這個協定需要寫程式，這裡是寫的地方」的工具，比一個每遇到一台裝置就長出一個
勾選框的工具更有用。

### 8.8 建議

**可以，就照可定址來設計**——對象是協定屬於暫存器型、具名參數型或 SCPI 型的裝置，而那
涵蓋了大多數工業串列設備。要預留的形狀：

1. **命令樣板放在連線上**，tag 上放一個位址字串。光是這一個決定，就足以讓 tag 表維持
   只有一張。
2. **定位器階梯**，結構化的在前、regex 在最後。
3. **框架與檢查碼放在連線層**，永遠不要放進 tag。
4. **逐 tag 的命令覆寫**留給例外，讓規則的情況保持空白。
5. **能扇出到多個 tag 的交易**，因為整包回覆與請求合併都需要它。

**現在**要決定的：只有上面這個形狀，而且只需決定到「足以阻止 `modbusBinding` 變成三向
分岔」為止（§6 第 4 步）。**等真實裝置到手**再決定的：定位器的詞彙、框架的選項、檢查碼
的清單——這些應該對著一個存在的協定來寫。對著想像中的裝置設計出來的定位器階梯，四個級
距會剛好都錯。

最後是一條判準，套用在任何實際出現的裝置上：**畫面需要的每一個值，是否都能被命名、被
獨立詢問，並且在不需要記得前面問過什麼的情況下從回覆中找到？** 如果是，它就是可定址的，
屬於 tag 表。如果不是，它需要逃生口，硬塞進表格的代價會比直接寫程式更高。

## 9. 目前的抽象能同時撐住三種協定嗎？

**不能——但它只在三個明確的地方失守，而它做對的地方比做錯的多。** 問題不是設計方向錯
了，而是只有一種協定被實作過，這個抽象從來沒被要求扛第二種。

### 9.1 一個抽象必須切開的三層

| 層 | 它回答什麼 | 必須依協定而異嗎？ |
|---|---|---|
| **連線（Link）** | 線上是什麼，我怎麼跟它講話 | **要。** 串列參數、CAN 位元時序、UART 框架，三者毫無交集 |
| **值（Value）** | 這個數字是什麼，我怎麼取得它 | **一半。** *它是什麼*與協定無關；*它在哪裡*則有關 |
| **綁定（Binding）** | 這個值在畫面上驅動什麼 | **不要。** 一個追蹤數值的 slider 不在乎是哪條匯流排餵給它的 |

由此得到的檢驗只有一句話：**「Modbus」這個字，能不能從「值」的中立那一半、以及整個
「綁定」層裡完全刪掉？** 今天兩邊都刪不掉。

### 9.2 逐層檢視

| 層 | 今天有什麼 | 撐得住三種嗎？ |
|---|---|---|
| 專案設定 | `protocol` + `communication` + `canBus` 並排 | ⚠️ 可行，但每多一種協定就多一個頂層欄位 |
| Tag | `ModbusRegisterTag` **與** `CanSignalTag` 兩個完整型別 | ❌ **失守**——見 §9.3 |
| 元件綁定 | 只有 `ModbusBinding`，而且不分協定掛在每個元件上 | ❌ **失守** |
| 邏輯節點 | Read Tag／Write Tag，從 `communication.tags` 解析 | ⚠️ 形狀對了，接線還是 Modbus |
| 產生的描述子 | 13 個欄位裡有 11 個與協定無關 | ✅ 幾乎撐得住 |
| 韌體 runtime | `static modbus_rtu_async_client_t g_modbus_client`；一筆交易一個 binding | ❌ **失守** |
| Protocol 分頁 | 1104 行，一個頂層 `protocol === 'modbus-rtu' ? … : …` | ⚠️ 誠實的分岔——見 §9.6 |
| 兩個預覽 | 根本沒有模擬任何 tag | ➖ 因為沒做，所以中立 |

「元件綁定」那一列今天就有看得見的症狀：一個 CAN 專案的每個元件上，仍然會出現
**Modbus** 綁定編輯器，而且提供的 tag 清單是空的——因為 CAN signal 存在另一個欄位裡。

### 9.3 證據就在兩個 tag 型別裡

把它們並排：

| | `ModbusRegisterTag` | `CanSignalTag` |
|---|---|---|
| 身分 | `id`、`name` | `id`、`name` |
| 在哪裡 | `area`、`address` | `frameId`、`frameFormat`、`startBit`、`bitLength`、`byteOrder` |
| 是什麼 | `dataType: ModbusDataType` | `dataType: CanSignalDataType` |
| 存取 | `access: ModbusAccess` | `access: BusAccess` |
| 縮放 | `scale` | `scale`、**`offset`** |
| 排程 | `pollIntervalMs` | `pollIntervalMs` |

三件事很刺眼，而且沒有一件是真正的協定差異：

1. **`offset` 只有一邊有。** `raw × scale + offset` 是算術，不是匯流排功能。一個存
   「零下 40 度起算、單位 0.1 度」的 Modbus 暫存器，今天表達不出來；同樣物理量的 CAN
   signal 卻可以。那是抽象在漏，不是協定在差。
2. **同一個問題有兩套詞彙。** `ModbusDataType` 是 `uint16 | int16 | uint32 | …`——
   寬度*和*解讀擠在一個字裡。`CanSignalDataType` 是 `unsigned | signed | float32`——
   只有解讀，寬度在 `bitLength`。兩者描述同一件事，而且互相讀不懂對方。
3. **`BusAccess` 已經共用了。** `export type ModbusAccess = BusAccess` 只有一行，而
   那就是整個統一化——只不過只做在一個欄位上。接縫已經存在，只是寬度是一個欄位。

還有一件來自綁定那側：`ModbusWidgetProperty` 可以指向 `text`，但沒有任何 tag 型別能
帶字串。今天那代表「把數字格式化成文字」。一台回答 `RUNNING` / `STOPPED` 的 UART 裝置
會需要真的字串。

### 9.4 撐得住三種的模型長什麼樣

從 §9.1 推出來的切法：

```ts
interface Tag {
  id: string;
  name: string;
  /** 中立：不需要知道背後是哪條匯流排就填得出來。 */
  value: {
    dataType: TagDataType;   // bool | int | uint | float | string
    access: BusAccess;       // 今天就已經共用
    scale: number;
    offset: number;          // CAN 有；三種都該有
    unit?: string;           // 給標籤看的，不是給線路看的
  };
  /** 依協定而異：值在哪裡，以及怎麼排程。 */
  source: TagSource;
}
```

其中最吃重的一個決定，正好解掉 §9.3 的第二點：

> **語意型別屬於「值」，位元寬度屬於「來源」。**

`uint16` 是兩件事共用一個名字。把它們拆開，三種協定就共用同一套詞彙：Modbus 說*無號、
暫存器 N 上的兩個位元組*；CAN 說*無號、frame 0x123 第 8 位起 12 bits*；UART 說*無號、
從回覆解析出來*——完全沒有寬度，因為文字沒有寬度。

排程遵循同一條規則。輪詢間隔對 Modbus 有意義；對「frame 什麼時候來就什麼時候更新」的
CAN signal 沒有意義；對 UART 則屬於**命令**而不是屬於值。所以它應該待在 source 裡，讓
「被動接收」的來源乾脆沒有這個欄位——而不是像今天那樣掛在 `CanSignalTag` 上、卻什麼也
不代表。

### 9.5 撐得住三種的 runtime 形狀

三個動作，每種協定都只是把它們填滿：

| | 請求 | 解碼 | 排程 |
|---|---|---|---|
| **Modbus** | 讀 A 起算的 N 個暫存器 | 暫存器 → 值 | 每個 tag，可合併 |
| **CAN** | *沒有* | frame 酬載 → 好幾個 signal | 由到達驅動 |
| **UART** | 一行命令 | 回覆 → 一個或多個值 | 每個命令 |

`hmi_runtime.c` 已經有這個東西的 Modbus 版：`hmi_transaction_t` 帶著種類、重試次數與
逾時，上面還有一個輪轉游標決定下一個輪到誰。要讓它服務三種，只需要兩個改動，不需要重新
設計：

1. **交易要能扇出。** 它今天只握一個 `hmi_binding_state_t *`；而 CAN frame 與 UART
   整包回覆都是「一次事件更新好幾個 tag」。
2. **傳輸層要變成介面。** `static modbus_rtu_async_client_t g_modbus_client` 是具體的
   全域變數，但它上面那層迴圈其實已經是通用的了。

### 9.6 哪些**不**該統一

一個什麼都涵蓋的抽象等於什麼都沒涵蓋，所以有兩樣東西值得原封不動：

- **連線層。** 鮑率、同位、unit id 在 CAN 沒有對應；位元率、取樣點、FD 在串列沒有對應；
  框架與檢查碼是 UART 獨有。一個共同的「連線」型別，不論選哪個協定都有三分之二是無關
  欄位。`communication` 與 `canBus` 分開是**對的**——代價只是每種協定多一個頂層欄位，
  那是誠實的記帳，不是滲漏。
- **Protocol 分頁的分岔。** 連線區塊上的 `protocol === 'modbus-rtu' ? … : …` 是 UI 在
  反映一個真實差異。不該分岔的是它下面那張 tag 表：那本來就是一張表、一個形狀，而今天
  是兩張。

區分兩者的規則：**協定真的不同就分岔，只是看起來不同就統一。** 連線真的不同；值不是。

### 9.7 建議

依「多快回本」以及「第二種協定出現前做不做得了」排序：

| # | 改動 | 何時回本 |
|---|---|---|
| 1 | 幫 Modbus tag 加上 `offset` | **立刻，只有一種協定時就回本。** 這是今天就缺的功能，不是為將來鋪路 |
| 2 | 統一成一套 `TagDataType`，寬度移進 source | 立刻——順便讓 Modbus tag 說 `uint32`、UART tag 說 `uint` 不必兩套 enum |
| 3 | `modbusBinding` 改成中立名稱，來源放進判別欄位 | 第二種協定之前；現在便宜，之後就是三向分岔 |
| 4 | 綁定編輯器依專案協定設閘門 | 立刻——CAN 專案不該被端上一張 Modbus tag 清單 |
| 5 | 一個 `Tag` 型別配 `source` union，取代兩張表 | 跟第二種「真的要實作」的協定一起做 |
| 6 | runtime 的傳輸介面 + 可扇出的交易 | 跟第二種「真的要實作」的協定一起做 |

第 1、2、4 項不管 CAN 或 UART 會不會出現都值得做：每一項修的都是**現有這一種協定**身上
就已經不對的東西。第 3 項是唯一有時限的。第 5、6 項應該等到第二種協定真的在做的時候
——只有一個實作的抽象，只是一個猜測。

### 9.8 要持續套用的那個檢驗

從現在起，每當要往 tag 或 binding 上加一個欄位：

> **這個欄位，不知道背後是哪條匯流排也填得出來嗎？**

可以 → 它屬於中立那一半，裡面不該出現任何協定名稱。
不行 → 它屬於 source，放在判別欄位後面。

套用到今天的欄位：`scale`、`offset`、`access`、`dataType`，以及所有跟元件有關的東西，
都屬於中立那半；`area`、`address`、`frameId`、位元視窗、命令樣板、回覆定位器，都屬於
source。它也解釋了目前唯一放錯位置的那個欄位：CAN signal 上的 `pollIntervalMs`——因為
你必須先知道「CAN 不輪詢」才答得出它該填什麼。

## 10. 抽象該放在哪一層，以及業界怎麼做

檯面上的提案——**在編輯器抽象，編譯後各協定維持自己原生的通訊方式**——方向是對的。
它只在一個具體的地方不完整；而業界的答案，是把這個問題**換掉**，而不是回答它。

### 10.1 直覺對，但少了一層

「編輯器抽象、韌體原生」是兩層。它需要三層，因為「原生」不能被容許變成「互不相干」：

| 層 | 知道協定嗎？ | 這裡放什麼 |
|---|---|---|
| **應用層**——畫面、綁定、邏輯、警報、趨勢 | **不知道** | 只有 tag 名稱，別無其他 |
| **Runtime**——排程、值快取、寫入佇列、重試、更新元件 | **不知道** | 一份實作，所有協定共用 |
| **Driver**——編碼請求、解碼回覆、交易規則 | **完全知道** | 每個協定一份，彼此不共享 |

只有兩層是陷阱：三種協定會變成三個產碼器，吐出三種互不相干的韌體形狀；然後 scale、
重試、過期、寫入佇列的錯誤會同時存在於三個地方，而且各自表現不同。編輯器對作者承諾
「這些都只是 tag」，韌體卻默默不同意——那正是這個工具在畫布與面板之間極力避免的那一類
謊言。

好消息是 `hmi_runtime.c` **已經**大致是中間那層。排程、快取、重試計數、寫入佇列、更新
元件全都與協定無關；屬於 Modbus 的是那個 client 全域變數，以及裡面的編解碼。

還有一個性質值得先講，好把「這樣會不會有成本」的疑慮擋在前面：**這個抽象發生在編輯期
與連結期，不是執行期。** tag 表是產生成 `static const` 陣列的，所以一個只用一種 driver
的專案就只連結一種 driver。抽象在面板上不佔任何位元組。

### 10.2 中立層必須做出的兩個承諾

這裡才是「抽象」與「改個名字」的分水嶺。有兩個問題在三種協定下有三種答案，而中立層
必須選一個並且守住：

**1.「寫入成功」是什麼意思？**

| | Modbus | CAN | UART 命令 |
|---|---|---|---|
| 寫入是 | 一個請求配一個回覆 | 送出一個 frame，signal 層級沒有回應 | 一行命令，通常有 `OK` / `ERR` |
| runtime 能確認嗎？ | 能 | **不能** | 通常能 |

如果中立層承諾「已確認」，CAN 守不住這個承諾；如果承諾「已排入佇列」，Modbus 專案就
失去了它本來就有的資訊。誠實的解法是承諾**已排入佇列**，並讓 driver 可選地把「已確認」
當成每個 tag 的一個品質旗標回報——於是畫面到處都能顯示「已送出」，而在匯流排說得出口
的地方顯示「已確認」。今天的 `writeBehavior` 是默默套用了 Modbus 的那個答案。

**2. 一個值的「年紀」是什麼意思？**

| | Modbus | CAN | UART 命令 |
|---|---|---|---|
| 值什麼時候到 | 輪詢時 | frame 剛好來的時候 | 命令被回答時 |
| 「從來沒到過」長什麼樣 | 逾時 | 無限期的沉默 | 逾時 |

輪詢型協定有錯誤碼；被動接收型只是「什麼都沒有」。所以中立層需要把**過期（staleness）**
當成每個 tag 的一等屬性——*有效*、*超過 N ms 未更新*、*從未收到*——而不是借用 Modbus 的
錯誤碼。runtime 已經有一半了：`cached_value_valid`。

這兩件事做對，抽象的其餘部分就順了；做錯，之後每加一種協定都會把它們拗得更歪。

### 10.3 成熟的 HMI 大廠怎麼做

這個模式在業界高度一致——Siemens WinCC / TIA Portal、Weintek EasyBuilder Pro、Rockwell
FactoryTalk View、三菱 GT Designer、Pro-face GP-Pro EX、研華 WebAccess、Ignition。以可
觀察到的行為描述：

| | 它叫什麼 | 形狀 |
|---|---|---|
| **Siemens WinCC** | *Connections* + *Tags* | 一個 tag 指名一個 connection、一個資料型別、一個以該 driver 自己語法書寫的位址（`DB1.DBW20`、`4x0001`）、一個採集週期，以及線性換算 |
| **Weintek EasyBuilder Pro** | *裝置清單* + 位址挑選器 | 物件的位址是「裝置 · 位址型別 · 編號」；位址型別下拉會隨選到的 driver 改變。內部記憶體（`LW`、`LB`、`RW`）不屬於任何裝置 |
| **Rockwell FactoryTalk View** | *Data servers* | tag 透過 OPC 或直連伺服器解析；位址就是 PLC 自己的 tag 名稱 |
| **Ignition** | *中間放 OPC-UA* | 上層一律是 OPC tag，每個 driver 都是一台 OPC 伺服器。同一個想法的極端版 |

五件事它們全都一樣：

1. **裝置（連線）是一等物件，不是專案設定。** 你不會去設定「這個專案的協定」，你是新增
   裝置，每個裝置指名自己的 driver。
2. **tag 是抽象，位址保持原生。** 沒有人試圖讓位址在 driver 之間可攜。tag 帶名稱、型別、
   scale、死區、週期；位址則用該 driver 的方言書寫。
3. **存在不屬於任何裝置的內部 tag。** HMI 自己的狀態是一等公民——見 §10.7。
4. **tag 以上一律與協定無關**：畫面、警報、趨勢、配方、腳本、排程。
5. **一定有逃生口**：巨集語言、「自由協定」編輯器，或 driver SDK。沒有任何廠商宣稱表格
   能涵蓋所有裝置。

還有一件事**沒有任何一家在做**：把協定做成專案層級、可以切換的選項。不是因為切換危險，
而是因為在他們的模型裡根本沒有東西可切——協定是裝置的屬性，而一個專案有幾台裝置就是
幾台。

### 10.4 讓問題消失的那個想法

把 `protocol` 從**專案**移到**裝置**，這份文件裡的每個問題都會換一個形狀：

| 今天的問題 | 有了裝置之後 |
|---|---|
| 「可以改協定是好設計嗎？」 | 不會發生。你是編輯或新增一台裝置 |
| 「我的 tag 會亂掉嗎？」 | 不會——tag 屬於裝置，裝置去哪它去哪 |
| 「建立時是不是該鎖死？」 | 不會發生 |
| 「這次切換會擱置什麼？」 | 看得見：那台裝置自己的 tag 清單 |
| 「能不能同時支援 Modbus 和 UART？」 | 依構造就可以 |

最後一列對這個產品不是假設。一台面板用 Modbus 讀 PLC、同時用 UART 命令跟條碼機或秤重
模組講話，是完全常見的工業配置。而且板子模型早就允許了：`BoardDefinition.protocols` 是
一個**陣列**，`edt-evk043027b` 宣告的是 `['modbus-rtu', 'can-bus']`——硬體上兩條線都拉了。
「只能一種」這個限制只存在於專案模型裡。

```ts
interface Device {
  id: string;
  name: string;              // 「PLC 1」、「Scanner」
  protocol: ProtocolId;
  link: LinkConfig;          // 依協定：串列參數／位元時序／框架
  enabled: boolean;
}

interface Tag {
  id: string;
  name: string;
  deviceId: string | null;   // null = 內部 tag，見 §10.7
  value: { dataType; access; scale; offset; unit? };
  source: TagSource;
}
```

專案的 `protocol` 欄位變成推導出來的——`devices[0].protocol`——直到「只能一台裝置」的
上限被解除，那時它就不再存在。

### 10.5 那麼，建立專案時該鎖死嗎？

**不該——而且鎖死比現況更糟。**

- 它並沒有避免混亂，只是把「我的綁定被擱置了」換成「我得整個專案重做」，同樣的損失
  加上更多工。
- 真實專案會在中途換裝置。客戶換了電表、PLC 換了廠牌、原型講 Modbus 而量產機講 CAN。
- 這塊板子本來就支援兩種協定，鎖死等於禁止硬體做得到的事。

正確的順序是：**現在先告知，之後再做裝置。** 在裝置模型出現之前，切換時應該說明它會
擱置什麼（§6 第 1 步）；裝置模型出現之後，這個問題就消失了。

### 10.6 位址的兩種寫法

這裡有一個真實的分岔，而且業界兩邊都有人走：

| | **A. 結構化 union** | **B. driver 方言字串** |
|---|---|---|
| 儲存 | `{ kind: 'modbus'; area; address }` | `address: "4x0001"`，由 driver 解析 |
| 編輯器 | 正規欄位——area 下拉、數值位址 | 一個文字框加上 driver 提供的驗證器 |
| 驗證 | 編譯期，在 TypeScript | 執行期，在 driver |
| 新增一個 driver | 要寫它的欄位 UI | **完全不用動編輯器** |
| 誰在用 | 協定數量不多的工具 | Weintek、Siemens——上百個 driver |

對這個產品：**現在用 A，外加一個逃生變體**：

```ts
| { kind: 'raw'; address: string }   // 給不值得做編輯 UI 的 driver
```

理由是規模。在兩三種協定、而且對編輯體驗要求高的情況下，結構化欄位比較好：Modbus 的
area 應該是一個下拉，而不是一段要人拼對的字串。B 贏在 Weintek 那種規模——上百款 PLC 的
型錄——那不是這個產品現在的位置，也可能永遠不是。`raw` 變體讓這個選擇不是不可逆的。

### 10.7 內部 tag——證明抽象成立的最便宜方法

每一家都有：Weintek 的 `LW`/`LB`、Siemens 的 internal tag。一個背後沒有裝置、住在 HMI
記憶體裡的 tag。對這個產品來說，它的價值比看起來高：

1. **它能在沒有第二種協定的情況下，證明這個抽象真的與協定無關。** 如果 `TagSource` 有
   一個完全沒有線路的 `internal` 變體，而畫面、綁定、邏輯全都照舊運作，那中立層就真的
   中立。這個測試**今天**就能做，只需要現有這一種協定——遠比「等實作 CAN 的時候才發現
   答案」便宜。
2. **它讓兩個預覽有東西可模擬。** 今天兩個預覽都不模擬 tag，綁定的元件顯示的是設計時的
   值。內部 tag 沒有裝置要模擬——預覽只要把值存著，讓 Write Tag 節點去改它就行。於是
   邏輯圖突然變成不用硬體也測得起來。
3. **它給 HMI 自己的狀態一個家**：操作員還沒送出的設定值、螢幕亮度、兩個畫面之間的
   「已確認」旗標。今天這些狀態無處可住——`LogicVariable` 是單張圖的區域變數，而專案層
   的 `variables: []` 是個休眠欄位，到處被寫成 `[]`、沒有任何地方讀。
4. **它是保留值（retained）的天然落點**——那些應該在重開機後還在、要寫進 flash 的值。

### 10.8 成熟的 tag 層還帶著什麼

這是廣度，用來校準。以下在前述產品裡都是標準配備，而這裡一項都還沒有：

| 功能 | 買到什麼 | 在這裡的成本 |
|---|---|---|
| **死區（deadband）** | 值沒有動超過 X 就不更新畫面 | 一個欄位加一個比較 |
| **區塊讀取** | 把相鄰暫存器併成一個請求 | 要花真功夫，但 9600 下收益很大 |
| **裝置狀態 tag** | 「裝置 1 在線嗎」、錯誤計數，可綁到元件 | 幾乎免費——`hmi_runtime_status_t` 已經在算了 |
| **值的過期狀態** | 元件可以區分「最後已知值」與「未知」 | §10.2；`cached_value_valid` 已有一半 |
| **帶 offset 的縮放** | `raw × scale + offset` | 一個欄位——而且 Modbus 今天就缺（§9.3） |
| **工程單位** | 標籤文字跟著 tag 走 | 一個欄位 |
| **模擬模式** | 沒有裝置也能用樣式驅動 tag | 內部 tag 一做就順便有了 |

第三列最鋒利：runtime 已經在數成功與失敗的交易次數，也知道通訊是否正常。把那些暴露成
唯讀 tag，「裝置離線」橫幅就變成一個綁定，而不是一個功能。

### 10.9 韌體那一刀實際切在哪

driver 介面很小，因為其餘一切都留在共用的 runtime：

```c
typedef struct {
    bool     (*begin)(const void *link_config);
    /* 組出下一個請求。被動接收型的 driver 回傳 false。 */
    bool     (*encode)(const hmi_request_t *request, uint8_t *out, size_t *len);
    /* 餵進收到的位元組；產出零個或多個 tag 的值。 */
    size_t   (*decode)(const uint8_t *in, size_t len, hmi_value_t *out, size_t max);
    void     (*poll)(void);
} hmi_driver_t;
```

留在共用層的是：輪詢排程、值快取與過期、死區、寫入佇列、重試與逾時、更新元件的路徑。
那就是今天 `hmi_runtime.c` 的絕大部分——這個檔案本來就是中間層，只是有一個 driver 被
硬接在裡面。

兩個值得講明的後果：

- **`encode` 回傳 false 就是 CAN 的容身之處。** 被動接收型的 driver 永遠不組請求；排程
  器就是沒有東西要送給它，全部的工作都在解碼路徑上。同一道門也讓 UART 裝置可以主動推
  送。
- **一台裝置一個 driver，不是一個專案一個。** 裝置模型一旦存在，runtime 就握著一個
  `{ driver, link_config, transport }` 陣列，而 tag 表說明每個 tag 屬於哪一個。

### 10.10 分階段的路徑

每一階段都能單獨出貨、也都單獨有用：

| 階段 | 改什麼 | 買到什麼 | 何時 |
|---|---|---|---|
| **0** | Modbus tag 加 `offset`；統一 `TagDataType`；綁定編輯器依協定設閘門；切換前先告知會擱置什麼 | 修的是現有這一種協定身上就已經不對的東西 | 現在 |
| **1** | 引入 `Device`，**上限一台**。`protocol` 變成 `devices[0].protocol`。tag 加 `deviceId`。把現有設定遷移成一台裝置 | 關鍵的一次改名；上限還在的時候 UI 完全不用動 | 第二種協定之前 |
| **2** | 一張 `Tag` 表配 `source`；內部 tag；Protocol 分頁變成 Devices 分頁 | 不必實作第二種協定就能證明抽象成立；讓預覽變得有用 | 與第二種協定同時或稍早 |
| **3** | 解除上限：多台裝置，可以是不同協定。runtime 導入 driver 介面 | 同一台面板上 Modbus **和** UART | 當真的有專案需要兩條匯流排 |

第 1 階段最關鍵，而且大致是機械性的：把今天那份單一設定包進一個只有一個元素的清單。
在它之後，每一步都變成「加東西」而不是「重寫」。

### 10.11 現在該決定什麼

**現在就要決定的：**

- `protocol` 屬於裝置、不屬於專案——就算裝置清單被鎖成一台鎖上一年也一樣。正是這個決定
  讓後面每一步都變成累加。
- §10.2 的兩個承諾：寫入承諾**已排入佇列**，確認度做成每個 tag 的可選品質；值帶著
  **過期狀態**，而不是一個 Modbus 錯誤碼。
- tag 的中立半邊與 source 要分開，語意型別放在值、位元寬度放在 source（§9.4）。

**現在不要決定的：**

- UART 的定位器詞彙——它需要一台真的裝置（§8.8）。
- 未來的 driver 要用結構化位址還是方言字串。先走結構化，把 `raw` 變體留作出口。
- 多台裝置同時運作的細節——留空間就好。

**不要做的：**

- 在建立專案時鎖死協定。那是拿一個可回復的問題，換一個不可回復的。
- 抽象連線層。串列參數、CAN 位元時序、UART 框架三者毫無交集，把它們併成一個 union，
  不論選哪個協定都有三分之二是雜訊（§9.6）。

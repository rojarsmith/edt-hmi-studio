## [Unreleased]

### Added
- **A QrCode widget, in a new Image category above Miscellaneous** — a QR code computed from its content, with the QR standard's own knobs under the standard's own names: version 1–40 or auto (the smallest that fits), scale in pixels per module, and all four error-correction levels. The content comes from a **Texts-library resource, read in English** whatever language the panel is showing — a QR code is scanned by a phone, not read by the operator, and the address behind it does not translate — or from a **literal** typed into the widget (default `https://bitdove.net`); and on top of either, a **string sent over communication replaces it at run time**: the widget binds to a block of 1–64 consecutive registers carrying ASCII two characters each, high byte first, zero-ended, which is a new `string` data type running the whole way down — binding editor, binding generator, and a text path in every board's runtime that re-encodes **only when the words actually change**. Every layer draws the same code: the design canvas encodes the real content into SVG, the Prototype into Canvas 2D rectangles, the Simulator and the generated firmware run the very `qrcodegen` encoder LVGL bundles — called directly, because LVGL's own `lv_qrcode` wrapper pins the correction level to MEDIUM and picks the version itself, and both are settings this widget hands to the user. The property editor does the arithmetic on its foot line — which version the content needs, how many pixels that is, and whether it fits the widget's box — and a pinned version that cannot hold the content is an error with the fix in it, while the panel keeps the previous picture rather than drawing half a code. Pure software, so unlike Video it builds for every board; `LV_USE_QRCODE` is on in all four LVGL configurations. See [docs/components/qrcode.md](docs/components/qrcode.md)
- **A Video plays a playlist now, from anywhere on the card** — the single file name grew into three things. Each entry may carry its **folder in front of it**, either slash accepted, because a Windows user types what their own screen shows. The widget takes a **list of files**, typed one per line in play order — or scans a **folder** (the card's top level by default) and plays every .avi in it, in name order, up to 64 of them, scanned when the widget starts so a re-inserted card is picked up. A multi-file list plays **in order** by default; **Random order** draws the next file from a software random sequence, seeded differently every run, and never picks the one that just played — with Loop off it plays as many files as the list holds and stops; with one file named the switch is inert, since one file has no order to shuffle. A file that will not open is **skipped, not fatal**: a playlist is a set of separate videos, and only when every member fails does the widget say why. Loop now means the playlist. A project saved before playlists carries its old single `fileName` and plays it unchanged — every layer reads the props through one normaliser. The generated code hands the firmware a constant playlist table instead of one name, and the editor's checks grew to match: a wrong extension names the entry, a duplicate is pointed out, and a folder scan is left to the panel, which is the only thing that can look
- **An Information pane in the dock, and it speaks up when a video is picked** — a fifth pane between **Work** and **Build Firmware**, the first one that is not a log: it says what the selected component needs from the panel, in the words of the person placing it. A video on the panel hides whatever overlaps it, is shown at its recorded size rather than the widget's, and plays a file from a card the editor has never seen — none of which the canvas can show, where a video is a black box with a file name on it. The first project with a video put a button on top of it, and the panel showed the video and no button. So selecting a video now makes Information the front tab of the strip — without opening a collapsed dock, since selecting a widget is the commonest thing a designer does and a drawer that opened on every click would be taking the canvas away for a note — with the eight rules a video lives by and, above them, what *this* one breaks on *this* screen: `Button_2 overlaps this video`, `The video runs off the screen`, `No file named yet`, with a *Ready to play* / *2 reminders* verdict in the toolbar — reminders, not faults, since nothing here stops a build. The overlap check flattens the screen into absolute boxes and skips the video's own containers and anything hidden. It comes forward only on a new selection, so switching to Work while the same video stays selected is not undone; selecting any other widget leaves the dock alone, since for those the pane has nothing to add. Nothing in it names LVGL, a layer, a codec or a buffer, and a test keeps it that way. See [docs/bottom-dock-panel.md](docs/bottom-dock-panel.md) §12
- **A Video widget that plays a film off the SD card** — a new **Miscellaneous** category in the Components panel, holding the one widget whose content the project does not own. Every other widget is compiled into the firmware image; a minute of 800x480 footage is around 200 MB, two hundred times the internal Flash of the board that would play it. So a Video **names** its file instead of holding it: you type `intro.avi`, the panel finds that file in the root of its SD card at run time, and nothing about it enters the build. A two-hour clip costs the firmware image exactly what a two-second one does — nothing — and changing the video means swapping the card rather than rebuilding. It has three properties and no more: the file name, **Auto Play**, and **Loop**. The format is **Motion JPEG in an AVI container**, and that is not a preference: it is the only common format whose per-frame work is exactly what the STM32H747's JPEG codec peripheral does in hardware, and DMA2D reads the codec's MCU-block output directly and writes raster ARGB8888, so there is no CPU in the pixel path at all. A frame costs a few milliseconds against a 41 ms period at 24 fps, and the main loop keeps running Modbus and touch between them. Because playing video needs that codec and an SD interface, it is the first widget whose feasibility is a property of the **silicon** rather than of a driver we have not written — a Cortex-M7 is not going to decode 24 JPEGs a second in software while also drawing a UI, so there is no slower path to fall back to. It is therefore gated exactly as an unimplemented protocol already is: the widget can be placed, configured, previewed and saved on any board, and a project using one **cannot be built** for the F746G-DISCO or the EVK043027B, with the Video section and the Deploy tab both saying why. A project that has no video pays nothing for this — `--gc-sections` drops the runtime and its 3.1 MB of SDRAM buffers entirely, measured at **+20 KB of Flash** for a project that has one and byte-for-byte no change for one that does not. What the panel says when it cannot play is kept as specific as what it can act on: **Video not found** for a name that matches nothing on the card, but **No SD card** when the slot is empty and **SD card unreadable** when the card is there and the file system is not, because telling someone their video is missing when they simply forgot to push the card in sends them looking in the wrong place. Neither the design canvas, the Prototype nor the Emulator plays anything — none of them has the panel's card reader, and none has ever seen the file — so all three draw the frame the picture will occupy with the file name across it, rather than inventing a still. The firmware side is four new modules on the H747I: an AVI demuxer that streams the `movi` list and never reads the index, so memory does not grow with the length of the film; the JPEG-and-DMA2D decode; a read-only FatFs over the board's microSD socket, with `disk_*` implemented straight against the BSP and `FF_FS_READONLY` on so nothing this firmware does can alter a card; and the widget runtime, which opens nothing until the widget is actually on screen. Audio is demuxed past and not played — see [docs/video-playback.md](docs/video-playback.md) §7 for that and the four other things this deliberately does not do
- **An Emulator build is now a Work item, and its output arrives while it runs** — pressing Start used to be a button that went quiet: nothing appeared in the **Work** pane, which lists every other long-running operation, and the Build Output pane stayed empty until the whole thing finished. Both are fixed by reusing what the firmware build already had. The build streams over the **same SSE channel and the same endpoint** (`/api/hmi/build-log/:runId`), so the pane fills as the compiler works and the summary lands at the end of that transcript rather than replacing it — the compiler's output is streamed once and the summary omits it, so nothing prints twice. And the build appears in **Work** like any other operation, moving through *Preparing your screens*, *Compiling the display engine* on a first run, *Compiling your screens*, and ending as *Running in the Emulator* or *Could not build your screens*. Those phases come from an allow-list matched against markers the dev server emits on purpose, never from parsing compiler output, so nothing raw can surface in the product's view of the operation. Because Work is on every tab, a build started on Preview stays visible after switching to Design
- **The Build Output pane says what the build did, instead of the word "succeeded"** — it used to report exactly `Build succeeded`, because the server returned only a build id and the client supplied those two words, so **every warning emcc produced was collected and thrown away**. It now reports the elapsed time, which LVGL was used and where it was found, whether the static library was compiled or reused from the cache, what was compiled, the size of the `.wasm` and `.js` that came out, and then everything the compiler said — with a warning count above it, because the same deprecation arrives once per translation unit and the count is what makes the tail scannable. Switching it on immediately surfaced four warnings that had been produced on every build since LVGL 9.5 arrived: `wasm/lv_conf.h` still spelled `LV_FS_DEFAULT_DRIVE_LETTER`, which 9.5 deprecates in favour of `LV_FS_DEFAULT_DRIVER_LETTER` and quietly aliases, so the rename silences all four and the pane now ends with "emcc said nothing — no warnings". Changing that file changes the LVGL library's cache key, so the first build after this takes minutes again while the library is recompiled
- **The Emulator's build output moves into the bottom dock, on a Preview-only tab** — it used to live behind a `📋 Build Output` toggle that opened a box **over the Emulator's own canvas**, which is the wrong shape twice: it is a build log, and this product already keeps build logs in the drawer above the status bar; and the moment you most want to read it — a build has just failed — is the moment you also want to see the screen behind it. It is now a **Build Output** pane sitting between **Work** and **Build Firmware**, which is ladder order rather than alphabetical: the Emulator compiles before Deploy does, so the two build logs read left to right in the order a project passes through them. It carries the same Copy and Clear the firmware log has, and a failed build brings it to the front and opens the drawer if it was collapsed, so the output arrives without being asked for. It is also the dock's first tab-specific pane: unlike Work, which lists operations that outlive the tab that started them, this one describes what the *Preview* tab just did and would be a log for something off-screen anywhere else — so the strip is filtered rather than the drawer hidden, and leaving Preview resolves to Work without writing that choice down, which means coming back lands on Build Output again
- **Preview opens the Emulator, and the three rungs are named for what they are** — the sub-tab strip is gone from normal use: opening **Preview** now opens the **🎛️ Emulator** directly, because that is the only rung that runs your code and a green result on either of the others is an answer about the editor rather than about the panel ([docs/preview-ladder.md](docs/preview-ladder.md) §8). The other two are renamed to say what they actually are, rather than how quick they are: **Quick Preview** is **📱 Prototype** — the editor's own Canvas 2D drawing, with zoom, click-through navigation and animation playback — and **LVGL Preview** is **🖥️ Simulator** — real LVGL drawing your screen with none of your code in it. Choosing between the three joins the rest of the factory-dev tools, where the audience is someone working on the editor and the difference between the rungs is the thing being worked on; a build with `VITE_ENABLE_EMULATOR=false` keeps the strip in both modes, since hiding it there would leave the remaining two rungs with no way in. The Emulator's own footer — the LVGL version and the compiler that built it — moves behind the same flag for the same reason: it answers "why does this differ from the board", which is not a question a panel author is asking, and the panel above it already says everything they need. The new names run through the documentation as well, including the 46 widget references that had been calling them "Simple preview" and "LVGL WASM preview" — the phrase [docs/preview-ladder.md](docs/preview-ladder.md) §6 had deliberately left alone while rung 2 and rung 3 were both "the WASM preview", which is a reason that stopped applying the moment rung 2 got a name of its own
- **The Preview tab's third rung is now the 🎛️ Emulator, and it starts** — the rung that compiles the generated C against real LVGL and runs it in the page was called **Build & Run**, and on any checkout but one it did neither: `emcc` and LVGL were looked for at two absolute paths inside a contributor's Linux home directory, so the answer to pressing the button was a toolchain error naming a stranger's folders. It is renamed for what it is — the panel without the panel — with **Start** and **Stop** on the button, because a tab is a place and a button is an action. And it is made to work: `server/emulator/toolchain.ts` searches for each tool through an ordered list of candidates, each confirmed by a sentinel file rather than by a directory existing, with explicit configuration first, the pinned copy this repository installs second, and the machine's own last — and the winner named in the panel, so a surprising build is traceable to the copy that ran it. **LVGL is found in the firmware boards' dependency caches**, which means that on a machine that has built firmware once there is nothing to download and, better, the Emulator and Deploy compile the *same* LVGL at the *same* pin instead of agreeing by discipline. What is missing is installed by **`npm run emulator:setup`** — Emscripten 6.0.8 and LVGL v9.5.0 into a gitignored `.hmi-cache/emulator/`, nothing system-wide, following the same pinned-archive convention the firmware bootstrap already uses, down to reusing an archive from `firmware/vendor/` matched by the commit GitHub stamps into the zip. The static library the link needs is no longer a manual step nobody mentions: it is built on demand, cached by the configuration that produced it, compiled one job per core with its output streamed as it happens, and built with `LV_USE_SDL` off — which is why the old script could never have succeeded against LVGL 9.5 in the first place. Before any of that runs, the tab asks the dev server what it can build with, so a machine without a toolchain **says so with the command that fixes it** rather than after a compile that was never going to start, and says once that a first run takes minutes and later ones take seconds. Windows is a first-class target here rather than an afterthought: Git Bash is located next to the `git` that cloned the repository rather than trusted to PATH, and Emscripten's environment is constructed directly instead of sourced from `emsdk_env.sh`, which on Windows reaches for `python3`, meets the Microsoft Store's placeholder, and exports nothing at all. The whole plan, including the five defects behind the one error message and the four things it deliberately does not fix, is in [docs/emulator.md](docs/emulator.md)
- **Landscape or Portrait, chosen when the project is created and changeable afterwards** — a **Display Orientation** field joins Hardware Model Number in the New Project dialog, and the same field sits under Project Name in Project Settings for a project that already exists. Changing it there turns the design: every widget's box on every screen rotates a quarter turn, each subtree inside its parent's pre-rotation frame rather than inside the canvas, and the canvas transposes with them — one undo entry, so Ctrl+Z takes the whole thing back. Boxes only, and the dialog says so before it saves rather than after: a label's text direction, an arc's angles and a chart's axes are a design question per widget type, not a geometric one. The stored resolution is the *logical* one, already turned, which is why the forty-odd places that read the canvas size needed no change at all — including Prototype, Emulator, the alignment tools and the card thumbnails. Board definitions declare which orientations their firmware can drive, and that gates **building, not designing**, exactly as an unimplemented protocol does: both orientations can be laid out and previewed on every board, and the Deploy tab refuses the ones no driver exists for, naming the reason. Portrait is free on the STM32H747I-DISCO, whose OTM8009A is natively portrait and is turned landscape by the BSP writing the panel's own MADCTR register — no CPU, no extra RAM, and the tear-free DIRECT render mode untouched. The two parallel-RGB boards have no scan-direction register at all and would need LVGL's partial render mode with a software rotate on every flush, so their `board_display_init` refuses a portrait config rather than drawing a sheared screen. The orientation reaches the firmware as data, not a preprocessor define: a generated `hmi_display_generated.c` overrides a `__weak` default in each board's `board_display.c`, the same contract `hmi_runtime_config` uses, so a template with no generated source still links and boots. Verified with the ARM toolchain — both boards build, the strong definition wins when the file is present and the weak default links when it is not. The whole evaluation, including the LVGL constraint that makes the other two boards expensive and the 437 KB SRAM measurement that decides it, is in [docs/display-orientation.md](docs/display-orientation.md)
- **A component's event can run logic graphs — the Event Trigger finally has a caller** — Handler Type gains **Logic Graphs** beside Built-in Action and Custom Code: check one or more graphs and the event's callback calls each graph's event entry in list order. The component owns the wiring; the graph stays a reusable named action several events can run. The picker labels graphs that are inactive or have no Event Trigger, warns about empty and stale selections, and generated code comments out a graph that is deleted or switched off rather than calling a missing symbol. The Event Trigger node face lists its callers — `Called by: Button_a8da (CLICKED)` — and warns when nothing calls it. Under the hood every trigger got its own entry function: the graph function runs only event chains and each timer trigger owns a private callback, fixing two latent defects — a graph mixing timers and events cross-fired, and one delay-mode timer deleted the shared callback's timer for all of them. The whole history is recorded in [docs/logic-event-trigger.md](docs/logic-event-trigger.md)
- **Logic graphs speak tags, not registers — Read Tag and Write Tag** — the Protocol tab's tag table becomes the one place a Modbus address lives. The palette's Read Holding Register — an address typed into a node, exactly the protocol coupling a tag table exists to prevent — is deprecated (saved graphs keep working) in favour of **Read Tag** and **Write Tag**, which reference tags by name; the picker filters by access and says plainly which tags code generation cannot serve yet, and why. Read Tag covers 16-bit holding-register tags: polled raw over an object-less descriptor, the tag's type and scale applied in `ui_logic.c`, where an int16's sign survives the runtime read API's clamp. Write Tag is the write path that never existed — coil and holding-register tags of every data type, riding a write-only descriptor that carries the tag's type and scale, queued through the new `hmi_runtime_write_holding_register` / `hmi_runtime_write_coil` calls added to all three boards' runtimes (values are engineering values, scaled exactly as widget writes are; firmware verified by inspection and unit tests — the authoring environment has no ARM toolchain). First step of [docs/logic-node-taxonomy.md](docs/logic-node-taxonomy.md), which now records what landed
- **A logic graph gets a Properties panel, and an Active switch that really switches** — the panel joins the right side above Variables, the same collapsible shape as the graph list, showing the open graph's settings. Its one everyday control is **Active**: a graph switched off is absent from generated code entirely — declaration, function, callbacks and registration alike — and the panel says so. Graphs are treated as global for now, so the per-screen activation drafted alongside (all screens by default, an explicit checklist otherwise) moved behind Factory Dev Mode: stored on the graph, surviving save and export, consumed by nothing until code generation learns to gate on screens
- **The editor says, before flashing, what the device cannot draw** — the canvas renders with the browser's fonts, which cover every script, so a label showing 中文 through the built-in Montserrat looked perfect in the editor and rendered as boxes on the panel; the first sight of the failure cost a flash cycle. The Property editor's Typography section now checks each language's text — including the words a language without a value falls back to — against the font that will draw it on the device. Only the built-in Montserrat can gap: its coverage is fixed when LVGL is compiled, while a converted font's character set is collected from this same text. The warning names the languages and the characters, and points at the exact fix — a language tab with a covering font on the governing typography, or binding a typography when there is none. The Typographies panel's usage count also stops undercounting: it counted only the widget's own field, so a typography doing all its work through the Texts table read "Used by 0 widgets" — "safe to ignore" exactly when it is not
- **A real ellipsis for labels — "Ellipsis (…)" joins Long Text Mode** — LVGL's DOTS mode writes three ASCII periods, hard-coded in `lv_label.c` (`LV_LABEL_DOT_NUM`, not even a config option), so the single U+2026 TouchGFX offers meant doing the truncation ourselves: CLIP mode plus a generated helper that measures with `lv_text_get_size` and keeps the longest prefix that fits with the ellipsis appended, cutting only at UTF-8 boundaries. An ellipsis label linked to a text resource deliberately carries no translation tag — the label's own tag handling would restore the full text over the truncation on every language switch — so the generated callback owns the text and re-resolves the tag itself, re-truncating on language change and on resize. U+2026 is collected into the label's font automatically, or the tidy ending would render as a missing-glyph box. The canvas previews it with the browser's own single-line ellipsis, same character. The old `dot` option is now honestly labelled "Dots (...)". Verified compiling clean for Cortex-M7 under `-Wall -Wextra -Werror`
- **Wildcards, and a fallback character that actually renders** — a Modbus string or a formatted number arrives at runtime, invisible to the walk that trims the character set, so a typography can now declare Wildcard Characters and Wildcard Ranges (each side of a range is a literal character or `0x` hex — `0-9` means the digits, since code points 0–9 would be nine control characters). Declared per language tab, as TouchGFX shapes it: each tab carries its own Wildcards and Fallback Character fields, a tab that declares nothing inherits the Default's declaration, and each language's declaration is converted into the font that language resolves to — so an Arabic tab's `٪` lands in the Arabic face, not in every face. Ranges travel as `--range` rather than being expanded, because a declared CJK block is tens of thousands of characters and Windows cuts command lines at 32k. The Fallback Character rides the same declaration: generated code appends a substitute font to LVGL's `lv_font_t.fallback` chain whose `get_glyph_dsc` answers every letter with the declared character, sharing the source font's tables so it renders in the right face and size; a language declaring its own character gets its own substitute, switched with the language, and a tab that only adds wildcards generates no runtime switching at all — its whole effect is settled at conversion time — verified compiling clean for Cortex-M7 under `-Wall -Wextra -Werror`. Label and Button preview the full resolved typography on the canvas — spacing, alignment, decoration, per language — and their widget-level Text Alignment row hides while a typography governs them, since an object-local style would silently beat the shared one
- **Font glyph bitmaps are linked into external flash on the STM32H747I-DISCO** — a converted CJK subset is the largest thing this firmware links and 1 MB of internal flash has nowhere to put it beside the code. Each converted font redefines `LV_ATTRIBUTE_LARGE_CONST`, LVGL's own hook on that array, into a `.ext_flash_fonts` section the linker script places in the QSPI NOR; the descriptors, cmaps and `lv_font_t` stay in internal flash, since they are small and are read on every glyph lookup. Guarded on `HMI_FONTS_IN_EXTERNAL_FLASH`, which only a board with somewhere to put them defines, so the same converted file still serves the WASM preview and boards without external flash. Verified with the ARM toolchain: one 14px Noto Sans TC subset splits `.ext_flash_fonts` 0x148 / `.rodata` 0xcc, and the same file without the define is `.rodata` 0x214
- **Noto Sans SC ships with the editor too**, and all four Noto faces now sit under *Built-in* in the Typographies font dropdown — one heading, in the same place whether or not the project has added a font, with *Project fonts* left to mean what the author uploaded. The previous split showed the same font under two headings depending on whether it had been used yet, which is the editor's bookkeeping rather than anything the author chose. Montserrat is grouped with them while remaining a different kind of thing: compiled into LVGL, no conversion, only the sizes `lv_conf.h` switches on
- **Noto Sans TC ships with the editor** — Traditional Chinese is the primary market for these boards and was the one script with no bundled font, so switching a project to 繁體 rendered a row of tofu and the font dropdown had nothing in it that could fix that. `NotoSansTC-Regular.otf`, OFL-1.1, from the same `notofonts/noto-cjk` `Sans/SubsetOTF` build the bundled JP and KR fonts came from. It reaches Flash through the same auto charset trimming, so a UI's worth of Chinese costs tens of kilobytes rather than the 5.4 MB of the full face
- **A widget picks its text by key, from a dropdown** — the Property editor gains a Key field listing every row of the text table, so binding a widget is a selection rather than retyping its literal until it happens to match an existing row. Choosing a key refreshes the widget's literal to the words it now shows, which is what unlink and delete fall back to
- **A text resource can name the Typography its widgets render with** — a Typography column in the Texts tab, TouchGFX's TypedText → Typography pairing. Set there it wins over the widget's own assignment, so words needing a particular face carry it everywhere they appear rather than everywhere someone remembered. The canvas, the Property editor and `ui.c` all resolve through one shared rule, so the preview is the generated code
- **"Switch Language" as a built-in event action** — a button on the running UI can now change the language, which until now took hand-written C in a custom handler. Either a named language (`lv_translation_set_language("zh-TW")`) or "next language", which cycles through the project's languages and wraps; the cycling helper is emitted into `ui_events.c` once, whatever the number of buttons using it. Nothing else is generated because nothing else is needed — labels re-read their own text, and `ui.c` already registers callbacks for the widgets that do not. Two cases deliberately generate nothing rather than something that half-works: a language code the project no longer has, and cycling with a single language. See [docs/language-switching.md](docs/language-switching.md), which also sets out what the canvas 🌐 preview, Emulator and hardware each do and do not cover
- **Board support for the EDT EVK043027B** — STM32U599NJH6Q, 480×272 RGB888 panel driven straight from the LTDC, maXTouch MXT336U, and image resources in the MX25LM51245G OctoSPI NOR at `0x90000000`. Complete firmware template under `firmware/edt-evk043027b/`, including the vendored EDT panel and touch drivers. See [docs/edt-evk043027b.md](docs/edt-evk043027b.md)
- **Target identification for boards flashed by a standalone probe** — an ST-LINK/V2 on a flying lead reports no board name, so `probeBoardPattern` may now be `null`; the flasher connects without writing and checks the reported device ID against the board definition instead
- **Per-board external flash configuration** — the external loader name and base address moved from constants in `server/hmi/service.ts` onto the board definition, so each board names its own part. A board with `externalFlash: null` skips the external programming step

### Fixed
- **The Work tab's red lamp now lights for anything unfinished, not just firmware** — [docs/work-progress.md](docs/work-progress.md) §6 has always described it as "a red lamp on the Work tab whenever anything is running", but it was wired to the deploy store, which knows about a firmware build and a flash and nothing else. The first operation to join Work from elsewhere — the Emulator's build — therefore ran with the lamp dark. It now counts the Work items still running, and its tooltip names the one that is running or how many there are
- **The Emulator's LVGL library could be cached in a broken state** — the archive was assembled with `emar q` in batches of a hundred, and `q` appends, which is the wrong verb for building an artifact: two runs overlapping in one cache directory produced an archive of 592 members, 296 of them twice and a hundred missing, `lv_display.c.o` among them. It linked with `undefined symbol: lv_display_create`, and because the file existed it was cached in that state and every later build linked against it. The archive is now one `emar rcs` over a response file, checked against both the object count and the source count, and renamed into place only once complete — so a run that dies half way through leaves no library rather than a broken one, and two concurrent runs overwrite each other with equally complete archives instead of interleaving into one

- **The 48 codegen compile tests run instead of skipping, and the first run found a bug** — `src/codegen/__tests__/compile.test.ts` generates C and compiles it, which makes it the only place that checks the product's central claim, and it carried a fourth copy of the absolute toolchain paths above; `skipIf` was therefore true on every machine and the suite has reported "48 skipped" for its whole existence. It now resolves its toolchain the same way the Emulator does, and links against the library the Emulator has already built rather than starting a multi-minute compile inside `npm test`. Switched on, it immediately caught real output: a widget carrying text style properties but no font — letter spacing, a text decoration, a bare font size — emitted `lv_style_set_text_font(&ui_style_text_16, &_16)`, a symbol assembled from an empty font name, which does not compile. A text style that names no font now leaves the inherited font alone, which is what the per-widget path has always done

### Changed
- **The Emulator speaks the product's language unless you are in factory dev mode** — the status line said `Compiling your screens with LVGL…`, the canvas said `Press Start to run this screen on real LVGL`, the not-set-up panel listed Emscripten and a POSIX shell by name, and the Build Output pane carried the compiler's transcript. None of that is advice to someone laying out an HMI: they did not ask for LVGL and cannot act on a missing `bash`. Normally the panel now says **Preparing your panel…**, **Running — click the screen to try it**, and when the toolchain is absent it says who to ask and to use Deploy meanwhile. Factory dev mode keeps every word of the engineering version, which is where it is worth reading. The **Build Output** pane is deliberately outside this: it is the engineering view by definition, keeps its full detail in both modes, and is expected to move behind the flag whole rather than be translated into words a compiler transcript does not have. And the status line says **nothing at all while nothing is happening** — before the first Start and again after Stop, the button beside it already reports the state, so "Ready" and "Stopped" were repeating it
- **The Emulator's status line drops its emoji** — it read `⚡ Stopped`, `🔨 Compiling…`, `📦 Loading…`, and the symbols carried nothing the word beside them did not; ⚡ for an idle emulator read as a warning about something. The word stands alone now, with the two states worth noticing — failed and running — carried by colour instead, which needs no decoding. **Start** also leaves the toolbar once something is running, since a button offering to start an emulator that is already started says the opposite of what the panel beside it says; Stop is the only move left, and Start returns with it

- **The Edit Node dialog leads with a type chip, and keeps the machine name for the factory** — every node's dialog now shows a small category-coloured chip above the name field; the raw subtype identifier (`event_trigger`, `tag_read`, …) appears beside it only in Factory Dev Mode, by the reasoning that hides the Code tab. The Event Trigger's **Event Type dropdown is gone** — the component-side binding chooses the event, so the node had nothing left to configure; its dialog says where to bind instead, an `eventType` stored by older graphs is still read by the legacy registration invisibly, and the node face drops the stale Event line in favour of who actually calls it. Also fixes the dialog's type colours, which had missed the shelf rename and painted flow, screen and device nodes grey
- **Logic node categories are the shelves now, and the colours follow** — the stored five-way trigger-condition-action-data-custom becomes the six shelves (trigger / flow / screen / data / device / custom), so the display grouping and the data agree and the transitional `paletteGroup` field retires. Node colours track their shelf: Compare turned purple, Delay amber, the tag nodes teal, Call Function gray. The migration is the subType: `normalizeLogicGraphs` re-derives every node's category from the definition table at each store entry point — project open, project-list open, graph import — so files carrying `condition` and `action` read forever, and an unknown subType keeps a still-valid stored value or falls back to `custom`. Code generation keys on subType throughout; its one category check (the trigger-less linear fallback) now judges by execution inputs from the definition table, which also fixes its old blindness to `var_write` and `tag_write`
- **The Logic palette's Custom shelf moves behind Factory Dev Mode** — Call Function and C Code Block are hand-written C, the factory engineer's realm, by the same reasoning that moved the Code and Icon tabs there. The gate covers the shelf and the search alike, so custom nodes cannot leak back in through a query; nodes already placed in a graph keep rendering and generating in every mode — only the palette offer hides
- **The Logic palette regroups by what the author operates on** — Triggers / Flow / Screen / Data / Device / Custom, instead of the programmer's trigger-condition-action-data-custom. Delay moves to Flow (it is flow, not an action); Compare and Logic Operation join Data (they are expressions, and now sit with the other circle-port nodes); Get Property joins the rest of the Screen family; Call Function moves to Custom beside the C Code Block; Read Tag and Write Tag get a Device shelf that grows with protocols without growing nodes. Display-level only, per [docs/logic-node-taxonomy.md](docs/logic-node-taxonomy.md) decision 3: stored node types, their colours, and every saved graph are untouched, and a test pins both layers so they cannot drift silently
- **The Event Trigger's Event Object output moves behind Factory Dev Mode** — generated code discards the event (`(void)e;`), so in normal mode the port only promised what the device cannot deliver; one already wired stays visible in both modes so a connection is never stranded. The deeper finding is recorded in [docs/logic-event-trigger.md](docs/logic-event-trigger.md): an event graph generates code nothing registers, because the editor cannot yet say which component fires the trigger — a Target Component selector on the node's dialog was tried and deliberately taken out again while that design question stays open
- **Logic graphs get a manager panel below the node palette** — the graph selector was a dropdown floating over the canvas with a trash button beside it: in the way, and barely a manager. A collapsible Logic Graphs panel now sits under the Nodes palette — search, create, delete and click-to-open, with the open graph highlighted and a VS Code-style twisty leading the header row. The boundary with the palette drags to resize, and both sides keep a working minimum. Deleting confirms by name. Creating rejects a name another graph already carries and reopens the prompt with the rejected name, since two same-named graphs are indistinguishable in a list; the suggested default keeps skipping past taken names as before
- **The Icon tab moves behind Factory Dev Mode** — the library browses, searches and copies SVG, and all of that works, but nothing a no-code author can do with what it copies reaches the panel: the studio consumes no SVG, and the page has no insert step. A tab that leads nowhere is worse than no tab, so it joins Code as factory-dev-only until it grows a real pipeline. What *was* verified to reach hardware today — LVGL's built-in `LV_SYMBOL_*` glyphs pasted into a label's text (byte-verified through codegen), and Copy SVG → saved file → Image upload (rasterised to a correct ARGB8888 array) — is recorded with recipes and a symbol table in [docs/icon-library.md](docs/icon-library.md), alongside the agreed redesign direction
- **The Texts tab takes the tree-and-detail shape too, and Key is now Id** — TouchGFX's Groups pane: on the left a tree of groups (two levels, drag rows onto them) and text rows, synced with the table on the right — picking a group scopes the table to it, subgroups included; picking a row selects and scrolls to it in the table; ＋ New Text files into whatever group is in view. The Id column header sorts, ascending and descending, case-insensitively. The column is labelled Id rather than Key — and so is the widget binding dropdown in the Property editor — because it is the identifier generated code matches on, the same thing the Typographies tab's Id is. Adding a language moved from two loose toolbar inputs to a ＋ at the end of the column headers, where the columns are. Groups persist with the project and survive export/import
- **Font Properties splits what the author needs from what the factory needs** — in normal mode a selected font shows its metadata, its name, its rendered preview, and the warnings that matter to everyone: glyphs the file cannot draw, and places using custom C the character scan cannot see. The conversion machinery — C variable name, the Auto/Preset/Manual character-set modes, extra characters and ranges, coverage total, BPP and the generate buttons — sits behind Factory Dev Mode under a labelled divider, with Auto simply doing its job unattended. The panel also stops double-scrolling: the old inner 500px grey box is gone and the pane itself scrolls
- **The Fonts tab takes the Typographies shape: a tree on the left, properties on the right** — three fixed groups, collapsible: *Built-in* (Montserrat, compiled into LVGL — selecting it explains why there is nothing to convert or delete), *Bundled* (all four Noto faces, whether added or not; an unadded one is a row with **+ Add** and stays in this group once added instead of moving elsewhere), and *Project fonts* (what the author uploaded). Search, upload and delete live on the tree; the search filters every group. The Typographies font dropdown mirrors the same three groups, so both surfaces say "Built-in" and mean the same thing — compiled into LVGL — rather than one meaning that and the other meaning "ships with the studio". And bundled fonts are now default-present: every project gains all four Noto faces on open, with no + Add and no delete, because an unused font costs nothing — it is neither declared, converted, nor saved by payload — and a deleted one would only have reappeared on the next open. The + Add affordance survives solely as the degraded state for a payload that failed to load The old layout was a banner of unadded bundled fonts above a card grid of everything else, which was the same moving-target problem the Typographies font dropdown had
- **The Typographies tab is a tree, and each typography has a Default plus a tab per customised language** — TouchGFX's shape, and a fix for two things at once. A project with thirty sizes was a flat list nobody could scan, so typographies now live in groups, nested up to two levels and reordered by dragging, exactly as screens already are. And *Base font* is gone: a typography's own settings **are** its Default, a language tab stores only what it changes, and everything it does not name keeps coming from the Default — so giving 繁體 a CJK face is one field rather than a restatement of the style, and editing the Default still reaches every language that did not override it. Language tabs are added, not grown: only Default exists until the author picks a language from the ＋ menu, and every tab carries an × that closes it — the language then follows Default again, after a confirmation when the tab actually held settings and silently when it was empty. (TouchGFX hides the same removal behind a right-click; an × on the tab is the same act, visible.) A just-added tab is stored as an empty entry, so it survives a reload while generating nothing until it differs. A language may now override spacing, alignment, decoration and direction as well as the face, and generated code re-applies exactly those on a language switch, restoring the Default on the way out. Name is labelled Id, since it is what the generated style is named after rather than a description. Deliberately not offered: Fallback Characters, Ellipsis Character and the Bitmap/Vector switch — see [docs/text-typography-evaluation.md](docs/text-typography-evaluation.md) §7.1–7.3 for what LVGL can and cannot do there; a `fallbackCharacter` field is stored against the day wildcards make it meaningful
- **The Deploy tab's placement panel reads assets as ranges** — renamed from *Image Placement* to *Asset Placement*, listing converted fonts beside images and giving each one a start and an end address rather than an address and a size. The question it answers is whether an asset begins and ends inside the QSPI window, and two ends answer it directly; a range that starts in one region and ends in another now says so instead of reporting only where it began. A font row also carries its glyph count and the average bytes per glyph, counted from `glyph_dsc[]` in the file that was compiled — a size alone cannot say whether a font is large because it covers a lot or because each glyph is expensive
- **Font and size are two fields in the Typographies tab, not one dropdown** — pairing them made a single list carry both choices, so picking 24px meant scrolling past every font, and one font at two sizes read as two fonts. Font now lists families (Montserrat once, not 21 times) and Size is typed. The built-in only ships certain sizes, so it snaps to the nearest and says so
- **Bundled fonts are selectable straight from the Typographies font list** — Noto Sans JP and KR appear under "Bundled — added on selection" whether or not the project has added them, and choosing one adds it. Needing CJK coverage was a detour through the Fonts tab and back
- **No per-widget font control** — the Property editor sets a Typography and nothing else. A face and a size set on one widget were invisible to every other widget that ought to match it, and only a typography can carry a per-language font. "＋ New typography from this widget" still seeds one from whatever a widget already carries, which is how an older project moves across; existing per-widget settings keep generating as they did
- **Text keys are unique case-insensitively** — `newText` and `newtext` were two rows, and since auto-derived keys are lowercased, linking a widget showing "newText" created the second one right beside a hand-written first. One translated, one not, indistinguishable in the table. The rename now refuses it and says which key it collides with; auto-derived keys skip past a case-different one
- **EVK043027B runs 32-bit colour** — ARGB8888 rather than the packed RGB888 the vendor's TouchGFX demo uses, because this is an LVGL product. `LV_COLOR_DEPTH 32`, an ARGB8888 LTDC layer, `LV_COLOR_FORMAT_ARGB8888`, and a `FRAMEBUFFER` linker region grown from 768 KB to 1024 KB to hold two 510 KB buffers. All four have to agree; the linker script is the one that fails silently, by overlapping `.bss` instead of refusing to build

### Added
- **The EVK043027B verifies its own LTDC** — `HAL_LTDC_Init` and `HAL_LTDC_ConfigLayer` write registers and return `HAL_OK` without reading anything back, so with the bus clock off every write is discarded and both still report success. `HAL_LTDC_MspInit` is a `void` callback and could not report a failed PLL3 at all. `ltdc_clock_ready` now carries that result out, `ltdc_is_configured` re-reads `GCR`/`TWCR`/`CR`/`CFBAR`, and `ltdc_is_scanning` watches `CPSR` to prove the **pixel** clock is running — a separate clock from the bus clock, and invisible to every other check
- **Bring-up test pattern on the EVK043027B, off by default** — colour bars written straight into the frame buffer, bypassing LVGL, plus a backlight ramp. Splits "the display path is dead" from "LVGL is not drawing", and a backlit-but-black panel from an unlit one. Enable with `-DHMI_DISPLAY_BRINGUP_PATTERN_MS=10000`; a normal build boots straight into the UI
- **Status LED on the EVK043027B** — a steady 1 Hz heartbeat from the main loop, and in `board_error_handler` a repeating burst of `board_init_stage` + 1 flashes. It is the only output independent of the panel, its backlight and the switched supply rail, so it separates "firmware not running" from "firmware running, display misconfigured" without a debugger. See [docs/edt-evk043027b.md](docs/edt-evk043027b.md) §7

### Fixed
- **Choosing a Montserrat size the firmware does not compile in broke the build** — the Typographies tab offered all 21 sizes LVGL ships, but every target's `lv_conf.h` switches on only 12, 14, 16, 20, 24, 28 and 32. Picking any other generated a reference to a symbol that does not exist, failing with `'lv_font_montserrat_22' undeclared` about 540 files into a full LVGL compile. The offered set now comes from one constant, sizes snap onto it (ties round up), and a project already carrying an unbuildable size is snapped when opened. A test reads all four `lv_conf.h` files and fails if they and the constant ever disagree — they are not generated from one another, as [docs/lvgl-configuration.md](docs/lvgl-configuration.md) notes. `wasm/lv_conf.h` gains Montserrat 12 so the WASM preview and the boards offer the same set
- **Two logic graphs with the same name broke the firmware build** — both generated a function of the same name, and the duplicate only surfaced as `error: redefinition of 'logic_new_logic_graph'` at the end of a full LVGL compile. Accepting the "New Logic Graph" default twice was enough to reach it. The generator now assigns each graph a unique C name — the first keeps the plain one, later collisions take a numeric suffix — and `ui_logic.h` and `ui_logic.c` derive them from one shared function so a declaration cannot disagree with its definition. The editor also stops suggesting a name that is already taken
- **Every navigate event was listed as "Navigate to: Not set"** — the event panel read `targetPage`, the pre-rename spelling, while the editor has written `targetScreen` since the rename. Generated code was always correct; only the one-line summary in the list was wrong. Both spellings now display, so a project saved before the rename still reads properly
- **EVK043027B never got past the first line of `board_init`** — the PWR peripheral is clock gated on the STM32U5 (`RCC_AHB3ENR_PWREN`), so with its clock off `HAL_PWREx_ConfigSupply` polled a register that reads as zero and returned `HAL_TIMEOUT`. `HAL_Init` calls `HAL_MspInit` to supply that clock and the HAL's own is weak and empty; the vendor package has it in `stm32u5xx_hal_msp.c`, which this template had not ported. The clock tree, OctoSPI, LTDC and display were all never reached, and the only symptom was a dark panel
- **EVK043027B main loop stalled for seconds at a time** — the vendored maXTouch driver reads with 1000 ms I²C timeouts on both transmit and receive, and LVGL polls the input device every ~30 ms, so an absent or unresponsive touch controller blocked the whole HMI loop rather than merely degrading touch. `board_display_init` now probes the controller once with a 50 ms `HAL_I2C_IsDeviceReady` and registers no LVGL input device at all when it does not answer, recording the result in `board_touch_ready`
- **EVK043027B touch controller was never actually reset** — `CTP_RST` (PH6) was parked high, so on a warm reset the part was never taken through a reset at all. It is now pulsed low and released with the datasheet start-up delay
- **EVK043027B fault blink code was unreadable** — the spin-loop constant ran roughly eight times too fast, turning a twelve-flash stage code into a flicker
- **EVK043027B flashing failed at "Error: failed to erase memory"** — the board no longer links image resources into external flash, so nothing depends on an external loader. It was copied from the STM32H747I-DISCO template, where 1 MB of internal flash forces it; this board has 2 MB against ~285 KB of firmware and 383 KB for a full-screen 480×272 background, so images fit alongside the code with room to spare. The NOR is still fitted and still mapped at `0x90000000` for a project that outgrows internal flash — see [docs/edt-evk043027b.md](docs/edt-evk043027b.md) §4, which records why ST's `MX25LM51245G_STM32U599J-DK.stldr` cannot currently erase it
- **EVK043027B panel stayed dark after flashing** — `backlight_init` never called `HAL_TIM_MspPostInit`, so PE5 was never switched to AF2/TIM3_CH3 and the backlight driver received no PWM. `HAL_TIM_MspPostInit` is a CubeMX convention rather than a HAL callback, and the HAL declares no prototype for it, so the definition linked out as dead code while every HAL call still reported success
- **`FS_PW_SW` (PI15) left unasserted** — the vendor's own init drives this switched supply rail high before touching the panel; `panel_power_init` now does the same

### Changed
- **Start-up failures on the EVK043027B are now diagnosable** — `board_init` records its progress in `board_init_stage`, and a failure to bring up the OctoSPI NOR is no longer fatal: it sets `board_external_flash_ready` false and lets a project that uses no images run instead of blanking the panel with no explanation
- **Modbus RTU can now run over RS-485** — the EVK043027B drives USART2 through a transceiver with hardware driver-enable on PD4, rather than a UART wired to an ST-LINK virtual COM port. A PC needs a USB-to-RS-485 adapter to reach it; the Communication tab and the test server are otherwise unchanged
